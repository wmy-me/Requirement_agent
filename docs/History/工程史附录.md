## 1. 工程推进哲学

全仓库唯一的工程哲学声明，出自 `IMPLEMENTATION_PLAN.md` §11「关键设计原则」。四条原则**原文**：

> - 先保持行为一致，再优化架构
> - 先修正事实源，再处理流程编排
> - 先完成业务闭环，再完成异步能力
> - 先让代码可运行，再扩大功能范围

同文件 §12「后续动作」结尾点明了这套顺序要防的东西：

> 这能保证工程推进顺序稳定，并尽量避免"先写流程、后补数据库事实源"的反模式。

**解释力**：这四条解释了此后几乎所有重构的先后关系——为什么数据模型与 `commit_service`
先于 LangGraph 编排，为什么 Agent 接线先于多渠道路由，为什么异步 embedding 一直排在最后。
当后人问「为什么当初不先把流程画全」，答案在这段里，不在任何 issue 中。

## 4. SOCKS 代理排查手册

### 4.1 现象

在经 SOCKS 代理出网的环境中，`httpx` 建立客户端时若缺少 `socksio`，会直接失败：

```text
Using SOCKS proxy, but the 'socksio' package is not installed. Make sure to install httpx using `pip install httpx[socks]`.
```

### 4.2 代理变量清理清单

启动任何需要出网的进程（当时是 MCP 客户端）前，先清掉代理环境变量，避免 httpx 自动读取：

```bash
unset HTTP_PROXY
unset HTTPS_PROXY
unset ALL_PROXY
unset http_proxy
unset https_proxy
unset all_proxy
```

### 4.3 端口占用排查

「服务起不来」先怀疑旧进程占端口，而不是代码：

```bash
ss -lntp | grep 8000            # 看谁占着端口
ps -ef | grep 'uvicorn'         # 找到旧进程
kill <PID>
```

### 4.4 结论的固化位置

该结论**已被固化进 `../../pyproject.toml`**，见 `httpx` 依赖上方的注释（原文）：

```
# [socks] 额外依赖不可省：本环境经 SOCKS 代理出网，缺了它 httpx 会直接报
# "Using SOCKS proxy, but the 'socksio' package is not installed"，
# 所有 LLM 与 embedding 调用静默降级到启发式。
"httpx[socks]>=0.27.0",
```

### 4.5 该坑已复发过一次（2026-09-14）

**本次记录不构成已解决的历史问题——它在 2026-09-14 又发生了一次。**
提交 `808ab79`（fix(ingest)：长文本需求存不进库……并修复被我误删的 socksio）记载：
在引入 `pypdf` 后执行 `uv sync`，把 `socksio` 当作「未声明依赖」误删，于是
**所有 LLM 与 embedding 调用静默降级到启发式**，且因测试不打真实 LLM 而未被发现。
该提交同时把 `../../pyproject.toml` 中 `httpx` 的声明改为显式 `httpx[socks]`，用 extra 把它钉死。

**解释力**：这是一个「**失败是静默的**」型环境坑——它不报错、不崩溃，只让智能能力悄悄退化为
启发式规则，因此能潜伏很久。排查任何「模型表现异常但服务正常」的问题时，先看这里。

### 4.6 出网问题检查顺序

1. 端口是否被旧进程占用
2. 当前 Python 环境是否装有 `httpx[socks]`（→ `socksio`）
3. 是否存在 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` / SOCKS 代理变量
4. 是否误执行过 `uv sync` / `pip install` 把 `socksio` 挤掉

## 5. MCP 工具裁剪登记

MCP 层已从代码中整体删除，但删除时**工具集被裁剪过**。这是目前唯一的**能力回退线索**。

被删除前的 MCP 工具清单共 **12 个**（出自 `MCP_问题记录.md` §4 的实测工具列表）：

```

get_history_requirements          ← 已消失
get_master_requirements
create_master_requirement         ← 已消失
create_requirement_version        ← 已消失
update_master_requirement         ← 已消失
search_similar_requirements_by_text ← 已消失
append_audit_log                  ← 已消失
```

对照当时的 `src/requirement_agent/tools`（**该包已于 2026-09-16 整体删除**，原因与恢复方式见
`../refactoring/archive/deprecated-modules.md`；8 个方法：`health_check`、`ingest_channel_event`、
`submit_requirement`、`search_requirements`、`get_requirement_detail`、`get_requirement_versions`、
`get_master_requirements`、`submit_review_decision`），**消失的 6 个**是：

| 消失的工具 | 方向 | 说明 |
| --- | --- | --- |
| `create_master_requirement` | 写 | 直接创建主需求（现改走 `submit_requirement` + 人工评审） |
| `create_requirement_version` | 写 | 直接创建版本（现由 `commit_service` 在审核通过后自动完成） |
| `update_master_requirement` | 写 | 直接改主需求 |
| `append_audit_log` | 写 | 手工追加审计日志（现由业务链路自动落审计） |
| `search_similar_requirements_by_text` | 读 | 按文本查相似需求（现由渠道/检索链路内部完成） |
| `get_history_requirements` | 读 | 查历史需求（**纯读能力，无写替代品**） |

**判定（待确认）**：消失的 6 个中，4 个是「绕过评审直接写库」的写方法，删除方向与
`tools/__init__.py`（已删除，见上）中「不提供绕过评审的直接写主表方法」原则**一致**，基本可以判定为**有意裁剪**。
但 `search_similar_requirements_by_text` 与 `get_history_requirements` 是**读能力**——
读能力的缺失无法用「禁止绕过评审」解释。

> **⚠️ 待确认：这 6 个工具的消失，究竟是有意裁剪还是迁移遗漏？**
> 需要在归档前确认一次，尤其是两个读方法：
> - `search_similar_requirements_by_text`——今天「相似需求检索」是否还有等价入口？
> - `get_history_requirements`——今天「历史需求查询」是否还有等价入口？
>
> 若二者确无替代，则应作为**能力回退**登记；若已被内部服务吸收，则应在此注明去向并关闭此问。

以下片段不属于上述五类，但同属「源文档独有、别处无记载」的早期约定，一并留存备查。

**分层职责（`IMPLEMENTATION_PLAN.md` §1）**——早期对目录职责的硬性约定：

> - API 层只负责 HTTP 入口
> - MCP 层只负责工具适配

**事实写入边界（`任务清单.md` §二.6）**——「建议层 / 事实层」分离原则的原始表述：

> - AI 输出建议还没有专门的"建议层"和"事实层"分离

> - 不能让模型直接写入最终业务结果

（该原则原先体现在 `tools/__init__.py` 的「工具只做转发、不在此写库」中；该包已于 2026-09-16
删除，此后由 `application/` 层的写路径承担 —— 模型产出只作建议，落库一律经
`RequirementService` / `ReviewService`。）

**风险类型枚举（`IMPLEMENTATION_PLAN.md` §4）**——Risk Agent 的早期字段范围：

> Risk Agent：只保留 quality_risk / change_risk / technical_impact_risk

可作为迁移前的功能基线参照：
