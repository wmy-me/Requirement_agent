# 第一部分　长期记忆与多对话

> 来源：`/长期记忆与多对话_架构设计.md`（原自述「设计稿 v2」，实为已实施）。

## 1. 背景与目标

### 1.1 设计动机（原文保留）
- 当时会话状态存放在进程内 `chat_sessions: dict`，**重启即失**；服务端没有会话列表接口，前端只在 `localStorage` 里存了一批会话 id 索引。
- 已有相当完整的「需求语义底座」：Postgres + pgvector；`requirement_source` / `requirement_master` / `requirement_version` / `requirement_review` / `audit_event` / `outbox_event` 支撑「原始需求 → 抽取 → 评审 → 版本 → 审计」全链路；评审通过后经 `outbox_event`（`embedding_sync`）把正式需求编入向量库。
- 但这些记住的是**已入库的正式需求 REQ**，不是「和用户聊过什么、用户偏好什么、哪些想法被否了」。
- **最终回答缺口**：Agent 已能产出结构化卡片，但缺少真正面向用户的最终自然语言回答，且该回答没有进入会话历史。
- **重复消息现象**：前端曾出现「用户发送一次但 UI 显示两次」，源于乐观更新 + SSE + 历史回放之间缺少统一幂等键。

### 1.2 目标（三层）
1. **多对话持久化**：所有会话存库，重启/换设备后仍能列出并继续任一对话。
2. **长期记忆**：在会话之外沉淀可跨对话复用的记忆（要点、偏好、决策、被退回的想法、待办线索），并在**新对话**中自动召回。
3. **可治理**：记忆与需求全程留痕（来源会话可溯源）、可查看、可编辑、可删除。

### 1.3 贯穿性能力（F1–F5）
- **F1 最终回答**：每轮以 `assistant message` 收尾，`content` = 动态生成的 final_answer，`artifacts` = 结构化结果，二者同属一轮并持久化。
- **F2 消息幂等**：以 `client_message_id` 保证同一会话同一用户消息只落一条。
- **F3 Agent 执行可追踪**：以 `run_id` + `agent_run.status` 记录 running/completed/failed/cancelled。
- **F4 记忆治理**：记忆可失效 / 被替代 / 删除，且可溯源。
- **F5 actor 隔离**：conversation / message / memory / 召回均限定 `actor_id`。

## 2. 总体架构（原文保留）

```
┌────────────────────────────── 前端（单屏工作台） ──────────────────────────────┐
│  会话栏(服务端持久列表) │ 对话流(流式) │ 右栏：待办 / 需求库 / 审计 / [记忆库] │
│                        │  用户消息↓步骤↓卡片↓最终AI回答(final_answer)        │
└──────────────────────────────────────────────────────────────────────────────┘
                                        │
                                        ▼
┌────────────────────────────── 后端 ───────────────────────────────────────────┐
│  HTTP 路由（现有 /agent/chat/stream 等）                                        │
│    ├─ 会话层  ChatRepository  →  agent_conversation / agent_message            │
│    ├─ 运行层  RunRepository   →  agent_run（run_id + status）                  │
│    ├─ 记忆层  MemoryRepository →  memory_note (+ embedding vector)             │
│    └─ 召回层  MemoryContextBuilder：top-K 记忆 + 相关 REQ + 会话摘要            │
│  向量/嵌入：复用现有 pgvector + embedding 管线                                 │
└──────────────────────────────────────────────────────────────────────────────┘
```

〔勘误 E1〕架构图原文写 `memory_note (+ embedding vector(1536))`；实际列型已是 `vector(4096)`（见 §4.1）。

- 每轮处理统一收敛为：**用户消息 → 结构化治理结果 → Final Answer → assistant message → 落库 → 前端展示**。
- 全程复用现有 agent（extract/analyze/risk）、`retrieval_service`、outbox worker，尽量少改核心领域逻辑。

## 3. 第 1 层：对话持久化

### 3.1 数据模型（设计 DDL，已逐字落地于 `../../migrations/003_conversation_memory.sql`）

`agent_conversation` 承载会话级信息（标题、摘要、actor 归属）：

```sql
CREATE TABLE IF NOT EXISTS agent_conversation (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    actor_id    TEXT NOT NULL DEFAULT 'api-user',        -- actor_id：用户/租户隔离基础（F5）
    title       TEXT NOT NULL DEFAULT '新对话',
    summary     TEXT,                                    -- 会话摘要（可 LLM 滚动生成）
    status      TEXT NOT NULL DEFAULT 'active',          -- active | archived
    meta        JSONB NOT NULL DEFAULT '{}',
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS idx_conv_actor_upd
    ON agent_conversation (actor_id, updated_at DESC);
```

`agent_message` 承载单条消息。`client_message_id`（幂等，F2）、`run_id`（关联一次 Agent 执行，F3）；`content` 即最终自然语言 final_answer，`artifacts` 为该轮结构化结果：

```sql
CREATE TABLE IF NOT EXISTS agent_message (
    id                BIGSERIAL PRIMARY KEY,
    conversation_id   UUID NOT NULL REFERENCES agent_conversation(id) ON DELETE CASCADE,
    role              TEXT NOT NULL CHECK (role IN ('user','assistant','system')),
    content           TEXT NOT NULL,        -- user=原文；assistant=final_answer
    artifacts         JSONB,                -- assistant 的结构化卡片，原样保留
    client_message_id TEXT,                 -- 前端每次发送生成的 UUID（F2）
    run_id            UUID,                 -- 关联 agent_run（F3）
    meta              JSONB NOT NULL DEFAULT '{}',
    created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS idx_msg_conv
    ON agent_message (conversation_id, created_at);
CREATE UNIQUE INDEX IF NOT EXISTS uq_msg_conv_client
    ON agent_message (conversation_id, client_message_id)
    WHERE client_message_id IS NOT NULL;
```

`agent_run` 记录每次 Agent 执行的运行状态，用于幂等/失败恢复/前端状态展示（F3）：

```sql
CREATE TABLE IF NOT EXISTS agent_run (
    id                BIGSERIAL PRIMARY KEY,
    run_id            UUID NOT NULL DEFAULT gen_random_uuid(),
    conversation_id   UUID REFERENCES agent_conversation(id) ON DELETE CASCADE,
    client_message_id TEXT,
    status            TEXT NOT NULL DEFAULT 'running'
                      CHECK (status IN ('running','completed','failed','cancelled')),
    error             TEXT,
    meta              JSONB NOT NULL DEFAULT '{}',
    created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_run_once
    ON agent_run (conversation_id, client_message_id)
    WHERE client_message_id IS NOT NULL;
```

> 实际迁移文件额外包含：`update_updated_at_column()` 触发器函数与三张表的 `updated_at` 触发器、`memory_note` 建表（见 §4.1）、以及 `active` 投影列的初始回填 `UPDATE`。原文的这些写法是「建议归入」，实现时补全了触发器部分。

### 3.3 SSE / 服务接入（final_answer、幂等、run 生命周期）

一次请求按以下顺序处理（原文保留）：

1. **入参**：前端携带 `conversation_id`（无则新建）、`client_message_id`、消息文本。
2. **幂等判定（F2）**：按 `(conversation_id, client_message_id)` 查用户消息；**已存在 → 直接复用该消息对应的已有 assistant/history，不再重复执行**。
3. **创建/登记 run（F3）**：写入 `agent_run(status='running')`，用户消息**在 Agent 执行前先落库**（保证断连也有记录）。
4. **执行**：SSE 事件顺序为 `run`（下发 run_id）→ `step`×n → `artifacts` → `narrative`（final_answer 逐字流）→ `done`。
5. **收尾（正常）**：run 置 `completed`；assistant 消息（`content=final_answer` 全文，`artifacts=结构化结果`）落 `agent_message` 并回填 `run_id`；刷新 `conversation.updated_at`。
6. **异常/中断**：SSE 中途断开、浏览器刷新、网络重试、Agent 异常——若已完成但 SSE 未送达，前端重连/重放时按 `run.status` 复用已落库结果；Agent 异常则 run 置 `failed`；用户主动取消则 `cancelled`。**任何情况数据库都能查到「发生过这一次执行」，不会静默丢失。**
7. **前端不回放重复**：SSE 与 history reload 都按 `agent_run` / `client_message_id` 收敛。

〔勘误 E2〕原文此处写「`chat_sessions` 删除或仅作进程内缓存（落库为主）」。**实际未删**：`api/dependencies.py:78` 仍定义 `chat_sessions`，`agent_chat.py:294/615/703` 仍写入并作为历史读取兜底。落库为主已实现，内存态未清理。

### 3.4 前端改造（原文保留）
- 左栏「最近会话」由 `localStorage` 改为 `GET /conversations`。
- 「新对话」= `POST /conversations`；点会话 = `GET .../messages` 回放（复用 `renderHistory`，渲染顺序：用户消息 → 卡片 → final_answer 气泡）。
- 会话删除按钮 → `DELETE`（记忆不受影响，见 §4.4）。
- **重复消息修复（F2）**：发送事件里每次生成 UUID 作 `client_message_id`；submit handler 在「请求进行中」禁用按钮 + 幂等键判重；SSE 不回本地乐观插入，改以「用户消息先落库返回 id」为准；history reload 不做前端手动去重，由后端幂等保证唯一。重点检查点：`submit handler`、optimistic UI、SSE message 处理、`renderHistory`。
- **最终回答展示（F1）**：卡片之后显示独立 AI 气泡作为 final_answer（`content`），来自服务端落库文本，刷新后仍在。

### 3.5 最终回答 final_answer（F1）（原文保留）

一次需求处理收敛为一条 **assistant message**：

```json
{
  "role": "assistant",
  "content": "面向用户的最终自然语言总结",
  "artifacts": {
    "requirement": {},
    "related_requirements": [],
    "conflict_analysis": {},
    "risk_assessment": {},
    "review": {}
  }
}
```

要求：
- `content` = 最终自然语言回答；`artifacts` = 本轮结构化分析结果；二者同属一轮 assistant message，同落库、同回放。
- **final_answer 必须动态生成**：依据本轮真实结果，不能是前端写死的一句话，也不是内部 JSON/debug 信息。
- **不是普通分析卡片**：展示为独立的 AI 对话气泡，位于各分析卡片之后。
- 现有分析卡片全部保留。
- 实现归属：final_answer 文本由 Agent 执行层产出（分析图完成后经流式 LLM 生成），写入 `agent_message.content`；**非流式消费端**（如历史回放）直接读该字段即可恢复。

## 4. 第 2 层：长期记忆

### 4.1 数据模型与 `status + superseded_by` 的取舍

**为什么用 `status + superseded_by` 而不是单一 `active` 布尔（原文保留，本文核心）**：
`memory_note` 采用 **status + superseded_by**（而非单一 `active` 布尔），以满足「失效 / 被替代 / 删除」的治理语义；`active` 保留为兼容投影列（`active = (status='active')`），索引仍以 status 为准。理由是可以区分三种不同结局——「被新记忆取代」（`superseded`，可沿 `superseded_by` 回溯替代链）与「用户主动删除」（`deleted`，软删保审计）——单一布尔无法表达，且会丢失替代关系。

```sql
CREATE TABLE IF NOT EXISTS memory_note (
    id                    BIGSERIAL PRIMARY KEY,
    actor_id              TEXT NOT NULL DEFAULT 'api-user',        -- actor 隔离（F5）
    kind                  TEXT NOT NULL DEFAULT 'fact'
                          CHECK (kind IN
                            ('preference','decision','fact','idea','rejected','followup','requirement_ref')),
    status                TEXT NOT NULL DEFAULT 'active'
                          CHECK (status IN ('active','superseded','deleted')),   -- 治理状态
    active                BOOLEAN NOT NULL DEFAULT TRUE,   -- 投影列：active=(status='active')
    content               TEXT NOT NULL,                 -- 一条可读记忆（中文短句）
    source_conversation_id UUID REFERENCES agent_conversation(id) ON DELETE SET NULL,
    source_message_id     BIGINT,                        -- 来源消息（可选）
    ref_requirement_key   TEXT,                          -- 若指向某 REQ
    superseded_by         BIGINT REFERENCES memory_note(id),   -- 被哪条新记忆替代
    embedding             vector(1536),                  -- 去重 + 召回用
    importance            SMALLINT NOT NULL DEFAULT 1,   -- 1..5
    meta                  JSONB NOT NULL DEFAULT '{}',
    created_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at            TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS idx_memory_hnsw
    ON memory_note USING hnsw (embedding vector_cosine_ops);
CREATE INDEX IF NOT EXISTS idx_memory_actor_active
    ON memory_note (actor_id, status, importance DESC, created_at DESC);
```

### 4.2 记忆写入通道与准入规则（推荐「自动为主 + 手动为辅」）

写入链路统一为 **Memory Candidate → LLM 判断是否值得长期记忆 → 通过 → Memory Note**。

**自动抽取（finalize / 会话结束）**
- 触发点：用户点「新对话/归档」时调用 `POST /conversations/{id}/finalize`；或由轻量调度轮询「超过 N 分钟无消息的会话」。
- **候选与准入**：把该会话最近消息交给 LLM，先生成若干 **Memory Candidate**，再由 LLM 按下列规则判断是否值得沉淀；通过后才落 `memory_note`。
- **值得进入长期记忆（优先，原文保留）**：
  ① 用户明确表达的长期偏好；
  ② 用户明确做出的架构/业务决策；
  ③ 明确被否决的方案；
  ④ 后续仍可能影响 Agent 决策的重要事实；
  ⑤ 用户明确要求 Agent 记住的信息；
  ⑥ 与正式需求治理相关的重要决策/退回原因。
- **不要自动记忆（原文保留）**：
  普通闲聊、临时问题、一次性调试信息、临时测试数据、无长期价值的问答、Agent 自己推测但用户未确认的事实。

  〔勘误 E4〕本次交办原文称该负向清单「在代码里没有对应物，是唯一存档」。
  **代码事实**：`application/memory_service.py:80-88` 的 `MemoryExtractor.SYSTEM_PROMPT` 已内联了几乎同义的正/负两份清单（`【值得记忆】…` / `【不要记】…`）。故该清单**在代码中有对应物**，本节保留它是因为它是设计口径的完整表述，而非唯一来源。

- **去重**：原文设想——每条候选与同 actor 现有 `status='active'` 记忆做向量相似度（cosine），阈值（如 ≥0.88）命中则跳过或合并、累加 `importance`。
  〔补充事实〕当前代码的落点是：把 `existing_notes` 一并塞进 prompt，由 LLM 输出 `op ∈ {add, skip, supersede}` 来裁决；**没有**阈值化的向量去重代码路径（`memory.py` 无 0.88/相似度去重逻辑）。
- **替代（supersede）**：若新记忆与某条 active 记忆冲突或「覆盖更新」，把旧记忆置 `status='superseded'` 并写 `superseded_by=新记忆.id`，新记忆保持 `active`。代码中由 LLM 返回 `supersede_note_id` 触发，且校验 `old_id` 属于同 actor。
- 入库后同步产出 `embedding_sync` outbox 事件，复用现有 worker 计算向量。

**手动收藏**
- 对话流 final_answer 气泡/结论卡片增加「记住这条」：直接写入一条 `memory_note`（`source_conversation_id`/`source_message_id` 自动带上）；同样可指定「作为某条 active 记忆的替代」（触发 supersede）。
- 评审动作（通过/退回）自动追加一条 `decision`/`requirement_ref` 记忆；退回原因按「被否决的方案」对待。

**治理侧回填（低成本高价值）**
- 正式 REQ 已向量化；另外把**被退回的 source、评审意见、审计事件**里的要点按需沉淀成 `rejected`/`followup` 记忆，减少下次重复撞坑。

### 4.3 记忆召回（RAG 注入）（原文保留）

新会话每轮（或仅首轮 + 长会话摘要）由后端 `MemoryContextBuilder` 拼 `memory_context`：
1. `memory_note` **限定 `actor_id = 当前用户` 且 `status='active'`**，按 `content` 向量召回 top-K（默认 4）；**不召回 superseded / deleted**（F4、F5）。
2. `requirement_master` 相关 REQ（复用现有 `retrieval_service.search`）top-N。
3. 若为续聊，带本会话 `summary`。
4. 组装为一段只读上下文，注入 **final_answer / assistant 生成**的 prompt（也可按开关注入 extract/analyze，默认不注入以免抖动）。

**效果示例**：用户新对话说「按上次退款告警那套思路」，助手能带回旧会话里确定的阈值/渠道偏好，而不是只理解当前一句话。

### 4.4 记忆来源可追溯与删除语义（原文保留）
- **来源可追溯**：`memory_note` 通过 `source_conversation_id`（+ 可选 `source_message_id`）、`ref_requirement_key`、`created_at/updated_at` 完整定位「这条记忆从哪来」。
- **前端记忆库**每条记忆提供 **[查看来源]**：跳回产生该记忆的会话；若来源会话已删除（`ON DELETE SET NULL`），记忆继续保留，但展示「来源会话已删除」。
- **删除语义（区分「删会话」 ≠ 「删记忆」）**：
  - 删除来源会话：会话与消息级联删除；**记忆保留**，来源字段置空并提示「来源会话已删除」。
  - 用户删除某条记忆：**不做物理删除**，置 `status='deleted'`（`active=false`），保证审计可追踪。
- **状态流转**：`active → superseded(deleted)`；被替代时记录 `superseded_by`，形成可审计的替代链。

### 4.5 actor_id 与用户数据隔离（F5，硬约束，原文保留）
- 当前阶段继续用默认 `actor_id='api-user'`，但 `actor_id` 是未来用户/租户隔离的基础，接口与 Repository 设计**一律预留/透传 actor_id**。
- 隔离范围：`agent_conversation`、`agent_message`（经 conversation 归属）、`memory_note`、会话列表、记忆召回、需求相关用户私有数据。
- **`MemoryContextBuilder` 必须 `WHERE actor_id = 当前用户` 召回**，绝不跨 actor 检索，防止用户 A 的历史记忆被用户 B 的 Agent 召回。

# 第二部分　需求版本管理与溯源

> 来源：`/需求版本管理与溯源_实施方案.md`（原自述「设计稿 v1（未实施）」，实为已实施）。

## 1. 现状与差距 → 方案思路

### 1.1 当时的差距（原文保留）
- ✅ 已有 Git 式版本**骨架**：`requirement_master`（`current_version`、`lock_version`、`final_requirement`）+ `requirement_version`（`version_no`、`change_type`、`requirement_snapshot`、`change_summary`、`diff_payload`、`created_by/reviewed_by/created_at`、`parent_version_id`）+ `requirement_version_source`（版本↔来源）。
- ❌ 关键缺口：
  1. `canonical_requirement` 只把「**当前来源**」的文本生成/覆盖成整段快照 —— **没有跨来源按「功能行」合并/增删**；
  2. 只有 version↔source 的一次关联，**没有 feature-line 级「这一行源自哪个 REQ/来源」**；
  3. 无 diff 视图、无表格视图、检索缺「输入人 / 版本 / 结构化功能字段」维度。

### 1.2 方案思路（原文保留，本方案唯一的建模动机论述）
> **方案思路**：把「一条正式需求 REQ」从「一整段文本」升级为「**若干条功能条目（Feature）的有序集合**」，每次新需求入库 = 对目标 REQ 做一批 **feature 级 add/modify/delete**，形成新版本；每条 feature 记录**来源与生效区间**，从而既给出最终描述，也天然支持溯源与 diff。

## 2. 核心概念与原则（原文保留）

| 概念 | 含义 | 对应现有对象 |
|---|---|---|
| REQ（主需求） | 一个可演进的需求主体 | `requirement_master` |
| 版本（Version） | 对 REQ 的一次原子变更结果 | `requirement_version` |
| **Feature（功能条目）** | REQ 内一条最小、可独立增删改的功能描述 | **新增** |
| 来源（Source） | 从某渠道进来的一条需求 | `requirement_source` |
| **Provenance（溯源）** | 「这条 feature 来自哪个 source/REQ、哪个版本引入、何时被改/被删」 | **新增**（jsonb/外键） |

原则：
- 一条 REQ 的**最终需求描述** = 按序拼接其**当前 active 的 Feature**（确定性、可机器生成）。
- 每条 Feature 有**稳定标识 `feature_key`** 与**生效区间**（`created_version_no` … `removed_version_no`），从而任取版本 V 都能还原「当时该 REQ 长什么样」。
- 每个版本除快照文本外，额外记录**该版本的 feature 级变更清单**，便于 diff 与审计。

## 3. 数据模型（`../../migrations/005_requirement_feature_versioning.sql`）

〔勘误 E5〕原文标题与 §8 写「迁移 004 / `004_version_features.sql`」；实际为 `005_requirement_feature_versioning.sql`。

### 3.1 新增 `requirement_feature`（已逐列落地）

```sql
CREATE TABLE IF NOT EXISTS requirement_feature (
    id                  BIGSERIAL PRIMARY KEY,
    requirement_id      BIGINT NOT NULL REFERENCES requirement_master(id) ON DELETE CASCADE,
    feature_key         TEXT NOT NULL,                -- REQ 内稳定 key（如 F-001 / login.sms）
    content             TEXT NOT NULL,                -- 该功能条目的规范化描述
    status              TEXT NOT NULL DEFAULT 'active'
                        CHECK (status IN ('active','deleted')),  -- deleted=逻辑删除（审计保留）
    ordinal             INT  NOT NULL DEFAULT 0,      -- 展示顺序
    origin_source_id    BIGINT REFERENCES requirement_source(id) ON DELETE SET NULL,
    origin_requirement_key TEXT,                      -- 首次引入来自哪个 REQ（可为自身 key）
    origin_version_no   INT NOT NULL DEFAULT 1,       -- 引入版本
    removed_version_no  INT,                          -- 删除/失效版本（NULL=仍生效）
    provenance          JSONB NOT NULL DEFAULT '[]',  -- 变更史：[{version_no, source_id, requirement_key, kind, at}]
    content_hash        TEXT,                         -- 内容指纹，供 diff 去重
    created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at          TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_feature_req_key
    ON requirement_feature (requirement_id, feature_key);
CREATE INDEX IF NOT EXISTS idx_feature_req_active
    ON requirement_feature (requirement_id, status, ordinal);
CREATE INDEX IF NOT EXISTS idx_feature_origin_source
    ON requirement_feature (origin_source_id);
```

> 说明：`feature_key` 用「REQ 内稳定标识」而不是全局 id，方便跨版本引用同一功能；同 REQ 内新增后 `ordinal` 递增。

### 3.2 扩展 `requirement_version`（已逐列落地）

```sql
ALTER TABLE requirement_version
    ADD COLUMN IF NOT EXISTS feature_changes JSONB,     -- 本版本 feature 级变更
    ADD COLUMN IF NOT EXISTS parent_version_no INT;     -- 父版本号（便于线性 diff）
```

`feature_changes` 结构：

```json
[
  { "op": "add",    "feature_key": "F-001", "content": "..." },
  { "op": "modify", "feature_key": "F-002", "before": "...", "after": "..." },
  { "op": "delete", "feature_key": "F-003", "content": "..." }
]
```

`requirement_version.change_type` 现有 CHECK 已含 `new/add/modify/delete`：`new`=首次建 REQ；`add/modify/delete`=合并到既有 REQ 时的版本主类型。

### 3.3 版本↔来源
沿用 `requirement_version_source(version_id, source_id)`（一个版本可关联多个来源）。

## 4. 版本管理核心流程

### 4.1 提交/分析阶段（沿用 LangGraph 分析图）
`submit_requirement` 已在抽取时产出 `extracted.requirements[]` —— 把其中每一行视为本来源的 **feature 候选**，随 source 进入待审。

### 4.2 人工审核时的合并决策
`ReviewService.submit_decision` 增加可选入参：
- `target_requirement_key`：决定「**新建 REQ**」还是「**合并进既有 REQ**」。
  - 无 target → 沿用现状：approved 新建 REQ，change_type=`new`，该来源所有 feature 行全部 `add`；
  - 有 target → 进入**合并模式**：把「本来源 feature 候选」对目标 REQ 当前 active features 做 diff。
- `feature_overrides`：逐条冲突裁决。diff 自动给出建议 op，遇 `analysis.conflict` 或修改既有行时**必须人工确认**：
  ```json
  [{ "feature_key": "F-001", "op": "add|modify|delete|keep", "content": "人工改写后的描述" }]
  ```
- 规则默认值：新增行→`add`；与既有行高度相似但内容不同→`modify`（给 before/after）；用户在源里明确表达「移除/不再需要」→`delete`；完全重复→`keep/noop`（不产生变更，但仍记来源关联）。

### 4.3 版本提交（决策图 commit 节点改造）

在 `workflows/commit_nodes.py` 的 commit 节点内，把原先「写一整段 canonical 快照」升级为「**执行 feature ops 并落版本**」，事务不变：
1. 取目标 REQ（新建则 `allocate_key` 后先建 master）；
2. 依 `feature_overrides`/自动 diff 应用变更：
   - `add`：插入 feature（`origin_source_id`=本 source，`created_version_no`=新版本号，`provenance` 追加一条）；
   - `modify`：更新 feature.content，`removed_version_no` 不动，`provenance` 追加 modify 记录；
   - `delete`：`status='deleted'`、`removed_version_no`=新版本号（**不物理删**，审计可见）；
   - `keep`：不写 feature 变更，仅关联来源。
3. 计算新 `version_no = current_version+1`，写 `requirement_version`：
   - `feature_changes` = 本次 ops；
   - `requirement_snapshot` = **合并后 active features 的有序拼接文本**（确定性「最终需求描述」）；
   - `change_type` = `new | add | modify | delete`（取本次主 op）；
4. 更新 `master.current_version`、`final_requirement`=快照、`lock_version` 乐观锁递增；
5. `link_source`、审计、outbox embedding（注意：**master 内容变化后旧向量需按新 final 重算**，见 §7 风险）。

**末段（原文保留，建模动机的落脚点）**：
> 效果：一条 REQ 从「文本被整体覆盖」变成「**功能集合按版本演进**」——新需求可以只给某条 REQ 增加一个功能、改写其中一行、或明确下线一行，版本链条忠实记录每一步。

### 4.4 最终需求描述与溯源

- **最终描述**：`master.final_requirement` 始终 = active features 拼接（可由 repo 的 `join_active_features(requirement_id)` 重算并校验一致）。
- **溯源到行**：UI 中每条 feature 显示来源徽标（**原文文案**）：
  - 首次引入：`源自 REQ-X · 由 source #id（渠道/时间）引入 V{n}`；
  - 最近改动：`V{n} 由 source #id 修改`；
  - 已下线：`V{m} 删除`（保留灰显）。
  - 点击徽标可跳转到对应 source 的 trace/回放或对应 REQ 的版本视图。

### 4.5 版本 Diff

`GET /requirements/{key}/diff?from=V1&to=V2`（默认相邻版本）返回：
- `added`：仅在 V2 的 active features；
- `removed`：仅在 V1；
- `modified`：两边都存在但 content 不同（含 before/after）；
- `unchanged` 计数。

前端以红/绿/黄高亮展示，形成「Git 式 diff 观感」。已实现于 `infrastructure/db/repositories/review.py` 与 `api/routes/requirements.py`。

## 5. 表格视图（需求库）

**需求库（表格）**：列 = `REQ key / 名称 / 领域 / 状态 / 当前版本 / 功能行数 / 最近变更时间 / 最近来源(渠道·输入人)`；行点击进入详情。

**详情 = 三块联动**：
1. **最终需求明细表**（默认展示「当前版本」）：每行=一条 feature，列=`序号/功能描述/状态/引入版本/来源徽标`；可用版本选择器切到历史版本看当时形态。
2. **版本时间线**：V1…Vn，展示 change_type、时间、审核人、`feature_changes` 摘要。
3. **版本 diff**：选定 V(n-1)→V(n) 高亮增删改。

数据来源接口：`GET /requirements/{key}/features?at_version=` 与 `GET /requirements/{key}/diff`。
前端落地于 `../../static/index.html` 的 `#library-panel`，导出为 `/api/v1/requirements/export`。

## 6. 多维检索（按 版本 / 时间 / 输入人 / 功能）

在现有 `GET /requirements/search`（q + 渠道/部门/领域/密级/时间区间）基础上扩展，**新增筛选维度**：
- `requester=`（输入人：匹配关联 source 的 `requester_id/name`）；
- `requirement_version` / `has_version_ge=`（如「该 REQ 当前版本 ≥ n」）；
- 功能检索：`q` 命中范围扩展——不仅搜 `requirement_name/final_requirement`，也搜 **feature.content**，返回匹配到的 REQ 及命中的 feature 行；
- 保留时间区间（提交时间 / 更新时间）。

两类入口：`GET /requirements/search`（REQ 级）与 `GET /requirements/features/search?q=&status=`（feature 行级，精确到「哪条功能出现在哪个 REQ 的哪个版本」）。

## 7. 风险与备注（原文保留，修正见批注）

- **embedding 与版本一致性**：master 被 modify/delete 后，旧 `requirement_embedding` 需按最新 `final_requirement` 重算（沿用 outbox `embedding_sync`，payload 带 version_no 供版本化失效）。

  〔勘误 E3〕**仅半开**。`workflows/commit_nodes.py:251-259` 只在**审核通过**时 enqueue 一次 `embedding_sync`，payload 确实带 `version_no`；但向量存储无版本维度，写入为 upsert 覆盖——**没有版本化重算**，也没有按版本失效的机制。

- **冲突合并需人工裁决**：自动 diff 只是建议；凡修改/删除既有 active feature 或命中 conflict 的行必须由 `feature_overrides` 显式确认，避免「自动吞掉旧功能」。
- **行级溯源近似性**：无结构化的旧数据回填只能「按行拆分 + 该版本来源整体归属」，后续来源行归属以新录入为准；`provenance` 保留变更史以便审计更正。
- **feature_key 稳定性（原文保留，本节核心规则）**：合并改名/合并两行时允许新 key，但需在 **`provenance`** 记 supersede 关系，防止把不同功能当同一功能 diff。`provenance` 是 feature 的**变更史**结构（`[{version_no, source_id, requirement_key, kind, at}]`），替代链与改动痕迹都在此累积。
- **兼容**：`requirement_snapshot`/`master.final_requirement` 继续维护为纯文本，旧接口与 trace 不回退。
- **锁定**：同一 REQ 并发合并用 `lock_version` 乐观锁，冲突则要求重审。

## 8. 存量数据回填 —— VM1（原文保留）

## 9. 验收清单（原文完整保留）
