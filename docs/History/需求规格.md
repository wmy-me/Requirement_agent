## 1. 项目概述

本项目用于建设一个企业需求治理系统，统一承接来自飞书、网页、API、文档、图片等渠道的需求输入，并完成需求提取、检索、分析、风险评估、人工审核、版本治理与审计追踪。

系统采用 Python 工程化架构，围绕 FastAPI、LangGraph、PostgreSQL、pgvector、MinIO、Worker 进行实现。

## 2. 建设目标

1. 统一管理企业需求来源。
2. 支持需求结构化提取与标准化存储。
3. 支持历史需求、相似需求与冲突需求检索。
4. 支持人工审核、编辑、驳回与重新提交。
5. 支持需求版本治理、审计留痕与回溯。
6. 支持异步 embedding 与向量索引同步。
7. 支持外部系统集成。

> **现状批注（2026-09-14）**：以下 §5.4.1、§5.5.1、§5.5.2 是需求方提出的原始「Skill 可插拔」诉求。代码明确**不走插件路线**：当前 Skill 是 `../../src/requirement_agent/skills` 下的普通 Python 类（`BaseSkill` 子类：`AnalyzeSkill` / `ExtractSkill` / `RiskSkill`），无版本号、无动态加载、无注册表、无白名单与热插拔机制。这三节作为需求原文保留，描述的是目标能力，不代表当前实现。

#### 5.4.1 可扩展分析能力

需求分析不得只依赖大模型的自由判断，应采用“Skill 标准 + 规则校验 + 检索证据 + 大模型推理”的可插拔架构：

- 支持读取、注册和调用需求分析 Skill。每个 Skill 包含适用范围、输入字段、判断标准、输出 Schema、版本号、示例和置信度规则。
- 支持按业务域、项目、组织或租户配置 Skill，允许后续增加“重复判定标准”“冲突分类标准”“需求独立性标准”等 Skill，无需修改核心流程代码。
- 支持 Skill 编排：先执行确定性规则和相似度检索，再由大模型依据 Skill 标准进行判断；规则与模型结论不一致时标记为“需人工复核”。
- 分析结果必须结构化保存：结论、判定类型、置信度、依据需求 ID、证据片段、使用的 Skill 名称及版本、模型信息、执行时间和 trace_id。
- 支持规则阈值配置，例如文本/向量相似度阈值、冲突关键词、互斥状态、业务域边界和必填条件，并记录阈值版本。
- 支持离线评测和人工反馈：保存标注样本、人工修正结果和误判原因，用于评估 Skill 与模型效果。
- Skill 执行失败、超时或输出不符合 Schema 时，必须降级到规则结果并提示人工审核，不得阻断需求留痕。

### 5.5 风险评估

- 评估质量风险。
- 评估变更风险。
- 评估技术影响风险。

#### 5.5.1 可扩展风险评估能力

- 支持读取、注册和调用风险评估 Skill。Skill 应定义风险维度、评分量表、触发条件、权重、证据要求、处置建议和版本信息。
- 内置可配置的质量风险、变更风险、技术影响风险标准，并支持扩展安全、合规、数据、成本、交付等风险 Skill。
- 风险评估采用“规则初筛 → 历史案例/指标检索 → 大模型解释与补充”的方式；大模型只能生成建议，最终等级由规则、阈值和人工审核共同确定。
- 输出统一风险对象：风险类型、等级、分值、影响范围、发生概率、触发因素、证据、缓解措施、责任人、截止时间、Skill 版本和置信度。
- 支持风险等级阈值和审批策略配置，例如高风险必须人工审核，中风险要求补充材料，低风险允许自动流转。
- 支持风险结果的版本化、审计和回溯；需求版本变化后自动重新评估受影响风险，并展示风险升降级原因。
- 支持通过人工审核结果、实际缺陷和变更结果反哺 Skill 评测集，形成“评估—审核—复盘—优化”的闭环。

#### 5.5.2 Skill 管理与安全约束

- Skill 应以独立目录/包或配置记录管理，具备唯一标识、版本、状态（草稿/启用/停用）、适用范围和发布人。
- Skill 加载应采用白名单和权限控制，限制可访问的数据、工具和提示词，防止未授权 Skill 读取敏感信息或直接写入业务事实。
- Skill 调用过程必须记录审计日志；核心 Agent 只消费结构化结果，不允许 Skill 绕过 Application Service 直接修改数据库。
- 支持热插拔或配置化切换，新增/升级 Skill 时保留兼容版本，并可回滚到上一版本。

### A. 渠道接入基建（而非“加解析函数”）
- 统一 `ChannelAdapter`（channel → normalized source），插件式注册，新增渠道只加一个 adapter —— **未做**（`feishu_client.py` 为 stub，无注册机制）；
- Webhook **签名校验** + `event_id` **幂等** —— **未做**（当前幂等靠原文哈希 `idempotency_key`，弱；`source_event_id` 字段存在但未用于去重）；
- 🟡 已完成：消息队列 / 重试 / 死信 / 背压 —— `outbox.py`（`FOR UPDATE SKIP LOCKED` 认领、重试转 `dead_letter`）+ `../../src/requirement_agent/workers/tasks.py` 独立 worker（:8200）+ 业务侧 enqueue 已接线；
- 处理**状态机可见**：received → queued → parsed → extracting → analyzing → pending_review（枚举已有，缺驱动与展示）—— **未做**。

### B. 多模态与真实解析
- ✅ 已完成：PDF/Docx 文本抽取、截图 OCR（`document_parser.py`：pypdf/docx/PIL+tesseract）。
- 剩余：语音转写（可选）、真正进入多模态 vision 打分——目前图片走 OCR 文本，无视觉模型直接理解图像。

### C. 需求关系与变更影响
- 一张 **REQ 关系表**（subject、target、relation∈conflict/related/depends/duplicates_of、原因、来源 source_id、裁决人、状态）——支撑影响分析。**已建**（`requirement_relation`，迁移 `009`）：分析阶段的候选在审核通过时落库，`depends` 仅预留枚举、暂无产出方；影响分析的**传播计算**（谁最终依赖谁）仍未做；
- 🟡 已完成了一半：多来源同时改动同一功能 → `requirement_feature` 的 `sync_features`/`apply_overrides` 已实现 add/modify/delete 合并 + 人工裁决（`lock_version` 乐观锁仍在）。

### D. 安全与合规
- 真实身份/RBAC：现在 `actor_id` 是字符串、审核人固定 `api-user`；企业需飞书 SSO、用户→角色→权限（谁能看高密级 `sensitivity_level`、谁能审核）；
- 数据保留策略 / 导出 / 删除 / 归档（软删 + 审计）。

### E. 可靠性与可观测
- **embedding 与版本一致性**：master 被新版本 modify 后旧向量需失效/重算（现仅审核通过触发一次 `embedding_sync`）—— **未做**；
- 管道可观测 UI：前端无；但**后端 dead-letter/重试表与 worker 驱动已存在**（见 A）；缺前端与指标；
- 模型/成本核算、多环境配置、超时/重试策略 —— 部分（`openai_provider.py` 有超时与流式降级，但无成本核算/多环境）。

### F. 渠道输出闭环
- 审核/状态变化回写渠道（飞书卡片待办、催办、结果通知）——有飞书输入的企业，必然要飞书输出。

### G. 数据血统与审计视图
- 已有 `audit_event` + trace，应包装为面向审计的**一键溯源/回放**（谁·何时·从渠道哪句话 → REQ 哪一行）。

### H. 产品/协作层
- 表格视图、Excel/CSV 导出、版本 diff 高亮、多角色评论、时间线。

### I. 多用户/多空间
- `actor_id` 已预留但无隔离；飞书多群/多项目空间的权限与归属。
