### 3.2 🟡 仓储默认自建 session —— **43 个方法**

统一模式：

```python
def some_method(self, ..., session: Session | None = None):
    owns_session = session is None
    session = session or SessionLocal()      # ← 不传就自己开一个
    ...
```

**精确说法**：这 43 个方法**都支持**传入 session（所以不违反规则的「能力」），
但**默认自建**（所以不传时就是独立事务）。

**后果**：你的 L2 约束「控制事务边界」在**路由直接调用**的那条路径上不成立 ——
`SessionLocal()` 一开一提交，事务边界散落在每个仓储方法内部，
应用层想要的「一次用例一个事务」无从谈起。

> 反例（做得对的）：`ReviewService.submit_decision` 自己开 session，
> 然后**把同一个 session 传给所有节点与仓储** —— 那是正确用法。

## 6. 需要你定的三处

### 6.1 API 路由层在你的四层里没有位置 —— 但它是 86 处越层的根源

你的四层是：Repository / Application Service / 只读 Query Tool / 模型 Adapter。
**HTTP 路由不在里面。** 而现实是路由承担了大量编排（尤其 `agent_chat.py` 28 处、
`conversations.py` 12 处）。

三条出路，请你选一条：

| 选项 | 含义 | 代价 |
|---|---|---|
| **(a) 承认路由是「薄控制器」，只允许调 Service** | 把 86 处逐个下沉到 Service —— 会话下沉到 `ConversationService`、能力裁决下沉到 `CapabilityReviewService` | **工作量最大**（约 26 个写方法要下沉），但分层最干净 |
| **(b) 承认路由是 L2 的一部分** | 明确「路由 = Application 层的 HTTP 适配」，允许它调 Repository | 零改动，但**你的 L1-约束 1 要改写** |
| **(c) 只约束「需求主线」相关的路径** | 正式写入必须走 Service；会话/记忆/文档等周边允许路由直调 | 折中；需要明确划线 |

我倾向 **(c)** —— 因为 `agent_chat.py` 那 16 处会话/run 写入**与需求治理无关**，
为它们建一个 Service 层是形式主义；而**能力/关系/标题的裁决**（6 处）确实该下沉。

### 6.2 L3 的「区分没有结果与查询失败」——现有实现有一个不一致

现状：工具在「查不到」时返回 `ToolResult.fail(...)`。这与你的要求**方向相反** ——
「没有结果」是**正常结果**（比如「没有相似需求」），不该是 error 状态。

例：`get_requirement('REQ-NOPE')` → `fail`。但「这条需求不存在」对模型来说
是个**合法答案**，不是工具故障。

**建议**：区分三态 —— `success`（有结果）/ `empty`（查了，没有）/ `error`（查询本身失败）。
要不要加，请你定。

### 6.3 `submit_requirement` 这个「写工具」怎么处理

现有工具层里它是唯一写入口，写的是 `requirement_source`（进待审，不碰正式需求）。
你的 L3 说「该层默认只读」，L4 说「模型不能创建正式 requirement_master」——
**它两条都不违反**（它既不碰主表，也确实产生了一条数据）。

但它**不满足「该层只读」的字面要求**。

三选一：

| 选项 | 说明 |
|---|---|
| **(a) 保留，但标成 `read_only=false` 且只给 `analysis` 用，不给 `assistant`** | 用 `allowed_consumers` 区分（你 §六 的设计正好支持） |
| **(b) 从 L3 移出，放到单独的「提交入口」** | 概念最清楚：L3 纯只读 |
| **(c) 干脆不给模型** | 提交需求走界面，模型只做分析 |

我倾向 **(a)** —— 你在 §六 里已经设计了 `allowed_consumers` 这个字段，正好用于此。

### 8.4 实施中实测出来的三个发现

1. **检索是「召回优先」的，几乎不会返回空。** 连「zzz完全不存在的业务场景zzz」都能拿到

   → **模型不能把「有结果」当成「有相似需求」**，`similarity` 只是候选排序。
   这条写进了测试，免得有人误解。
2. **多传字段必须拒绝。** pydantic 默认忽略多余字段，于是模型编一个参数名时工具会

## 10. B2 与规划文档的差异（2026-09-17）

规划文档（`docs/Requirement_agent后端任务与前端重构规划.docx` §三 B2）要求了两条，
实测后**都没照字面做**，理由记在这里。

### 10.1 `requires_confirmation` 字段：**不加**

文档要求每个工具声明 `requires_confirmation`。

**不做的理由**：L3 层**不存在有副作用的工具**，这个字段会恒为 `False` —— 正是本项目
一直在清的「预留了但没人用」。而「需要人工确认」这件事**已经由数据自身表达**：
工具返回里带着 `review_status: proposed` / `status: pending_confirmation` /
`capability_status`，**逐条**比一个工具级布尔精确得多。

留着这个判断：**等第一个真有副作用的工具出现时再加**（那时它才不是死字段）。

### 10.2 「第二批分析工具」：5 个里只加 2 个

文档点名：候选召回、关系分析、风险评估、能力匹配、影响预览。实测后逐个定性：

| 文档要的 | 底层 | 调模型？ | 结论 |
|---|---|---|---|
| 候选召回 | 固定图 `retrieve_node` | 否 | ❌ **已有工具覆盖**（`search_requirements` / `search_features`），再加就是同一件事两套实现 |
| 关系分析 | `AnalyzeAgent.analyze` | **是** | ❌ **不做** |
| 风险评估 | `RiskAgent.assess` | **是** | ❌ **不做** |
| **能力匹配** | `CapabilityMatchService.match` | 否 | ✅ **已加**」 |
| **影响预览** | `ReviewService.preview_merge` | 否 | ✅ **已加** |

**分界线是「调不调模型」**：工具是给模型**取数据**用的。一个自己会调模型的工具意味着
「模型决定再叫一个模型」—— 成本不可控、结果不可预期，而且在固定图里本来就是编排的职责。
确定性的、纯读的才可以做成工具。

## 11. B2 第二批实施记录（2026-09-17）

新增两个工具，工具集 13 → **15**，全部只读。

### 11.1 `match_capabilities` —— 它的输入形状是被逼出来的

**它收 `source_id`，不收「一段需求描述」。** 因为 `CapabilityMatchService.match()` 吃的是
**抽取出的 `action`/`object` 候选**（`extracted["capabilities"]`），而那东西**只有 LLM
抽取之后才存在**，纯文本推不出来（`_capability_candidates` 只读 `payload["capabilities"]`）。
所以只读工具只能反过来：**拿一条已抽取过的来源，对当前词表重跑匹配**。

这也划清了它和 `get_capabilities` 的分工：那个看**当初落库的**关联，这个用**现在的**词表重匹配。

> ### ⚠️ 实施中最要命的一处：`persist` 默认是 `True`
>
> `match()` 的签名是 `persist: bool = True` —— **默认会真的往库里写能力提案**
> （`capability` 行 + `feature_capability` 关联）。一个只读工具如果在「查询」的名义下
> 漏传这个参数，就是**热路径上的静默写入**。
>
> 已显式传 `persist=False`（源码那条分支的注释是「预演：如实回报『会提议这条』，
> 但不建行」），并补了一条**数行数**的测试：调用前后 `capability` / `feature_capability`
> 的行数必须一模一样。

### 11.2 `preview_merge_impact` —— 输入干净的那个

`preview_merge(source_id, target_requirement_key, merge_mode)`，输入都是具体标识，
不需要任何前置的模型步骤。它和真正落库那条路**共用同一个 diff 内核**，
所以列出的增删改就是提交后会真实发生的。

两条测试：`union` 不产生删除；**`replace` 的删除清单必须带 warnings**。
另加一条「预览一行都不写」（数 `requirement_version` / `feature` / `master` 的行数）。

### 12.2 ⚠️ 一处刻意的偏离：**检索失败不降级**

文档要求「统一处理工具异常、超时、重试和**降级**」。前三样做了，**降级没做**，理由：

**检索是判重复的唯一依据。** 失败时返回空候选，`analyze` 会得出「独立」的结论 ——
而「错误合并污染版本链」正是这套系统要防的头号问题。一个因检索挂掉而漏掉重复的需求
被当成独立需求入库，代价**远大于**「这次分析失败、走 outbox 重试」。

所以 `retrieve_node` 选择 **记录 + 上抛**（`ToolInvocationError`），让失败走既有的可见路径：
分析图异常 → outbox 任务失败 → 重试 → 死信（运维页看得到）。

> 若将来确实要降级继续，**必须同时**把「未做重复检查」写进 `metadata` 并在审核页显示 ——
> 那是跨前后端的改动，不该在后端悄悄做半截。**半截降级 = 静默的假阴性。**

### 12.3 实施中踩到的两个坑（都是「第二事实源过期」）

1. **循环导入**：`workflows/agents_nodes → tools.invoker → tools/__init__`（它一口气
   import 全部工具）→ `preview_merge_impact → application.review_service →
   workflows.commit_nodes` —— 而 `workflows` 正处于**半初始化**状态，当场炸
   （实测 13 个测试文件收集失败）。
   修法：`tools/__init__` **只导出契约与注册表**，注册改成**按需加载**（第一次问
   「有哪些工具」时才 import）。

2. **手写模块清单过期**：`_ensure_loaded` 初版维护了一份模块名清单，我凭印象列了
   `find_streams_by_capability` 与 `get_capabilities` —— **那是上一版工具包的模块名**，
   新包里根本不存在，一调用就 `ModuleNotFoundError`。
   修法：改成 **`pkgutil` 扫目录**，不维护第二份清单。
