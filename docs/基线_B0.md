## 6. 下一步：B1 鉴权与权限底座

文档 §三 B1 要求：

- 接入 `API_AUTH_TOKEN`，实现统一 HTTP 鉴权
- 区分**只读 / 分析 / 待审核写入 / 审核决策 / 回滚 / 运维**六类权限
- 飞书 Webhook **豁免**普通 API Token（继续用飞书自身的签名 + Token + AES 校验）
- 统一 401/403 错误结构，带 `request_id`
- 为 `reviewer` / `admin` / `system_worker` 建立最小权限规则

**开工前需先定一件事**（文档没写）：**角色从哪来？**

现在只有一个 `API_AUTH_TOKEN`，而文档要求六个权限档次 + 三个角色。
可行做法有几种（单 token 全权 / 多 token 映射角色 / token 携带角色），
需要定下来才能动手。见 §7。

## 7. B1 待定：多角色怎么映射到调用方

| 方案 | 怎么做 | 代价 |
|---|---|---|
| **(a) 单 token = 全权** | 只校验 token 是否存在 | 零角色区分，**不满足文档的六类权限要求** |
| **(b) 多 token → 角色**（如 `API_AUTH_TOKENS='{"tok-admin":"admin","tok-reviewer":"reviewer"}'`） | 每个调用方拿自己的 token | 满足要求；**配置格式是新的对外契约** |
| **(c) 单 token + 角色头**（如 `X-Actor-Role: reviewer`） | token 校验身份，角色由头声明 | 简单，但**角色可被伪造** —— 只要拿到 token 就能自称 admin |

**建议 (b)** —— 它是唯一「角色不可伪造」的做法，且与「最小权限」的要求一致。
(a) 会让 B1 变成只做了一半；(c) 等于没做权限。

定下来之后，B1 的实施大致是：
1. 定义角色 → 权限档次的映射（写进 `config/settings.py`）
2. 写鉴权中间件（`api/app.py`，与现有的安全响应头中间件并列）
3. **豁免清单**：`/health`、`/static`、`/ui`、飞书 webhook、OpenAPI 文档
4. 401（无 token / token 无效）与 403（角色不够）分开，响应带 `request_id`
5. 审计：鉴权失败记一条
6. 测试：每个角色的正例与反例 + 豁免路径
7. **`docs/api-contract.md` 同步**（这是对外契约变更）
