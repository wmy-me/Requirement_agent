## 3. 数据表方案（迁移 021，只追加）

### 3.1 `agent_run` 改造（ALTER，不重建）

现有列够用度高，只补三列 + 放宽枚举：

```sql
ALTER TABLE agent_run ADD COLUMN IF NOT EXISTS run_type   TEXT NOT NULL DEFAULT 'conversation';
ALTER TABLE agent_run ADD COLUMN IF NOT EXISTS source_id  BIGINT;   -- 分析 run 的外部锚点
ALTER TABLE agent_run ADD COLUMN IF NOT EXISTS current_node TEXT;   -- 正在跑哪个节点
ALTER TABLE agent_run ADD COLUMN IF NOT EXISTS started_at TIMESTAMPTZ;
ALTER TABLE agent_run ADD COLUMN IF NOT EXISTS ended_at   TIMESTAMPTZ;

-- 放宽 status：补 queued / waiting_review / retrying
ALTER TABLE agent_run DROP CONSTRAINT IF EXISTS agent_run_status_check;
ALTER TABLE agent_run ADD CONSTRAINT agent_run_status_check
    CHECK (status IN ('queued','running','waiting_review',
                      'completed','failed','cancelled','retrying'));
```

**为什么 `run_type` 用默认值 `'conversation'`**：现有行全是对话 run，默认值让它们
语义不变、无需回填。

**⚠️ 枚举里没有 `paused`** —— 与追加文档 §3.3 一致。原先代码在写它、而 DB 的 CHECK
从不允许，那个 pause 端点已于 2026-09-17 **删除**（详见 §2.3① 与 §7.2）。
这里 DROP + 重加 CHECK 是为了**补上新增的三个状态**，不是为了 `paused`。

**⚠️ 并发隔离会静默失效**：现有两条唯一索引都建在 `conversation_id` 上
（`uq_run_once` 003:47、`uq_run_active_per_conversation` 012:11）。分析 run 的
`conversation_id` 是 NULL，而 Postgres 唯一索引里 NULL 互不相等 → **不受这两条约束**。
这本身是对的（分析 run 的互斥应该按 **source**，不是按 conversation），但要**显式补一条**：

```sql
CREATE UNIQUE INDEX IF NOT EXISTS uq_analysis_run_active_per_source
    ON agent_run (source_id)
    WHERE run_type = 'analysis' AND status IN ('queued','running','retrying','waiting_review');
```

### 3.2 `agent_run_event`（新建）

```sql
CREATE TABLE IF NOT EXISTS agent_run_event (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,  -- 007 起雪花 id
    run_id     UUID NOT NULL REFERENCES agent_run(run_id) ON DELETE CASCADE,
    sequence   INTEGER NOT NULL,
    event_type TEXT NOT NULL,
    node       TEXT,
    payload    JSONB NOT NULL DEFAULT '{}',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT uq_run_event_seq UNIQUE (run_id, sequence)
);
CREATE INDEX IF NOT EXISTS idx_run_event_run_seq ON agent_run_event (run_id, sequence);
```

- **`UNIQUE (run_id, sequence)` 是本表的核心**：它让「同一个 run 的事件流有序且不重复」
  成为**数据库保证**，而不是应用层的自觉。`after_seq` 回放的正确性直接建立在它之上。
- `sequence` 由应用层分配（`SELECT COALESCE(MAX(sequence),0)+1 ... FOR UPDATE` 或
  先在内存里排好批量插入）。**不建自增列**：那会跨 run 全局递增，`after_seq` 就没法按 run 解释。
- `ON DELETE CASCADE`：run 删了事件跟着删。目前没有删 run 的路径，但这是对的语义。

### 3.3 `tool_invocation`（新建）

列**直接照搬** `tool_call_record` 的现有形状（`tools/invoker.py:64-85`），不另发明一套：

```sql
CREATE TABLE IF NOT EXISTS tool_invocation (
    id                BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    run_id            UUID REFERENCES agent_run(run_id) ON DELETE CASCADE,
    tool_name         TEXT NOT NULL,
    arguments_summary JSONB NOT NULL DEFAULT '{}',
    result_summary    JSONB NOT NULL DEFAULT '{}',   -- 含 count 与 sample
    status            TEXT NOT NULL,
    elapsed_ms        INTEGER,
    error_message     TEXT,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS idx_tool_invocation_run ON tool_invocation (run_id);
```

`result_summary` 装的就是 `tool_call_record` 里的 `count` + `sample`（前 3 条的编号与余弦）
—— **已经在采样了，只是没地方放**。

### 3.4 `model_invocation` —— **建议推迟到 B3.1**

追加文档 §3.2 把 `model_invocation` 列在 B2.1 的建议数据结构里，但：

- §3.4 的事件类型清单里**没有任何模型事件**；§3.6 的完成标准也不提模型调用；
- §4.4 的「模型调用元数据」整节属于 **B3.1**（它的字段里 `task_type` / `fallback_from`
  这些概念是 ModelRegistry 引入的）；
- 本项目对「建了但没人写」的表非常敏感（见 §6 的死字段清单）。

**已决策：B2.1 不建这张表**，由 B3.1 连同 ModelRegistry 一起建。这是一处
**与追加文档的显式差异**（文档 §3.2 把它列在 B2.1 下），理由如上。

### 3.5 状态与事件枚举

- **Run 状态**：`queued / running / waiting_review / completed / failed / cancelled / retrying`
  （追加文档 §3.3 的 7 个；**不含 `paused`**，见 §3.1 与 §7.2）
- **节点状态**：`pending / running / completed / failed / skipped` —— **不建表**，
  它是事件的派生视图（`node_started`/`node_completed` 两条事件之间的区间），
  建表会多一份要同步的事实源。
- **事件类型**：`run_started / node_started / node_completed / tool_started / tool_completed /
  candidate_found / relation_found / risk_found / review_required / run_completed /
  run_failed / run_cancelled / progress`（追加文档 §3.4 全部采纳）

## 4. 接口方案

### 4.1 SSE：**只加字段，不改事件名**

现有 6 个事件名（`session/step/artifacts/narrative/done/error`）已被契约（`api-contract.md` §6）
与前端（`app.js:573-587`）消费。**改名是破坏性的，本批次不改。**

改动只有两处：

1. **每个事件带上 `run_id` 与 `sequence`**（放进 data，不改事件名）
2. **`_sse()` 增加标准的 `id:` 行**（值 = `sequence`），让 SSE 协议层的
   `Last-Event-ID` 语义成立

```python
def _sse(name, payload, *, seq=None):        # seq 为 None 时行为与现在逐字节一致
    head = f"id: {seq}\n" if seq is not None else ""
    return f"{head}event: {name}\ndata: {json.dumps(payload, ensure_ascii=False)}\n\n"
```

> ⚠️ **`narrative` 不能按 token 落库。** 它现在是逐 token 推送的（`agent_chat.py:455`），
> 一个长回答会产生成百上千条事件。落库策略：**节点/工具/状态类事件逐条落，
> `narrative` 只在结束时落一条完整文本**；实时 token 仍然直推、不落库、不占序号。
> 断线重连时靠 `artifacts` + 最终 `narrative` 恢复，而不是逐字回放。
> 这条取舍必须写进契约，否则「after_seq 回放」会被理解成能逐字重放。

### 4.2 新增查询端点（只读，`READ` 档次）

| 端点 | 出参 | 说明 |
|---|---|---|
| `GET /api/v1/agent/runs?source_id=N` | `{items:[run…]}` | 分析运行列表（按 source 反查） |
| `GET /api/v1/agent/runs/{run_id}/events?after_seq=N&limit=M` | `{items:[event…]}` | **断线回放的唯一入口** |
| `GET /api/v1/agent/runs/{run_id}/invocations` | `{tools:[…], models:[…]}` | 工具/模型调用明细（models 在 B3.1 后才有） |

**复用现有**：`GET /api/v1/agent/runs/{run_id}`（`agent_chat.py:826`）已经存在，
返回 run 行；B2.1 给它补上新列即可。

⚠️ 新端点要进 `api/auth.py` 的 `WRITE_SCOPE_RULES` 吗？**不用** —— 它们全是 GET，
按现有规则一律 `read` 档次。但 `test_api_auth.py` 有一条「每条写路由都被显式分类」的
断言，新增写端点才会触发它；本批次不新增写端点（除了 pause 的修复）。

### 4.3 `/runs/{run_id}/retry`

追加文档 §3.5 要求「支持取消、失败、重试和最终状态查询」。取消与状态查询**已有**
（`CancelledError` 分支 + `GET /runs/{id}`）；**重试没有**。

新增 `POST /api/v1/agent/runs/{run_id}/retry`（`ANALYZE` 档次）：把 `failed` 的 run
复制成一个新 run（`retry_of` 存入 `meta`），**不原地复活** —— 原地改状态会让事件流
出现「同一个 run_id 下前后两段不相干的历史」，序号语义会烂掉。

## 7. 兼容风险与待拍板

### 7.1 兼容风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **`agent_run` 是被对话路径共用的表** | 加列本身安全（有默认值），但放宽 CHECK 要确认没有代码依赖「只允许 4 种状态」 | 全仓只有 `chat.py` 读写 status；加一条断言测试 |
