## 一 现状：为什么不能只是「加几个页面」

当前前端（`static/`，**无构建步骤，纯静态**）：

```
index.html  160 行   app.js 1997 行   styles.css 510 行
布局：左栏会话列表 │ 中间对话 │ 右栏工作台
右栏 5 个 tab：待办 / 需求库 / 文档库 / 审计 / 运维
右下角浮层：需求库大表（筛选 + 导出）
```

**它是「对话为中心，工作台是附属」。** 而规划文档要的是反过来：
**治理工作台为中心，对话是其中一项能力**。

这不是加页面能解决的，有三个结构性问题：

| 问题 | 表现 | 为什么现在改比以后改便宜 |
|---|---|---|
| **没有路由** | 所有状态在一个页面里，靠 `state.sessionId` 与 tab 切换；**没法把「这条需求的审核页」发给人** | 加路由要拆掉全部 `renderXxx()` 的隐式依赖 |
| **没有数据层** | 31 处 `apiJson` 散在各处，各自处理加载/错误/刷新；同一个端点在不同地方被重复拉 | 引入统一的请求层与缓存是重构的地基 |
| **1997 行单文件** | 需求库、审核、版本、运维、对话全在一个文件里 | 拆文件必须先定边界，而边界就是本方案 §四 |

> ⚠️ **不要「渐进式改这个 app.js」**。它的组织方式是「一个页面 + 一堆渲染函数」，
> 在这个结构上叠加 8 个模块，只会得到一个 5000 行的文件。
> 正确的渐进是**并存**：新工作台另起，逐个页面替换，旧页面最后删（§七）。

## 二 目标与边界

**目标**：把「需求表格 + 详情 + 几个按钮」升级为需求治理工作台 ——
围绕**需求输入、分析、审核、版本、来源、运行状态**组织信息。

**边界**（沿用后端批次的原则）：

- **前端不反向决定后端事务边界**：审核通过、合并、回滚都只调既有端点，
  前端不做「先改 A 再改 B」的编排（那是后端事务的事）。
- **不引入后端没有的能力**：界面上出现的每个数都要有端点支撑；
  没有的数据**显示「未提供」而不是编一个 0**。
- **权限如实呈现**：`403` 说明角色不够，界面应当**灰掉**对应操作并说明原因，
  而不是让人点了才报错。

## 四 信息架构

规划文档给的一级导航照搬，但**每个模块下面的页面要落到可执行的粒度**。

```
总览            /app
需求工作台      /app/requirements
输入中心        /app/intake
智能分析        /app/analysis
审核中心        /app/reviews
版本与变更      /app/versions
来源与知识      /app/knowledge
系统运维        /app/ops
```

对话助手**不再占一个一级入口** —— 它是「随时可唤起的能力」（全局按钮 / 侧滑），
而不是一个要主动切过去的页面。这是与现状最大的差别。

### 4.1 总览 `/`

| 页面 | 区块 | 数据 |
|---|---|---|
| Dashboard | 待我处理（待审数、冲突数、高风险数、死信数） | 聚合 |
| | 系统健康（DB / LLM / Embedding / **向量来源**） | 3 个 health 端点 |
| | 近期活动（最近提交、最近审核、最近失败） | 聚合 |
| 趋势与分布 | 需求提交趋势（按周/月） | 聚合 |
| | 渠道占比、领域分布 | 聚合 |
| 风险与漏斗 | 风险矩阵（质量×变更） | 聚合 |
| | 审核漏斗（提交→待审→通过/拒绝） | 聚合 |

> 整块由 `GET /stats/overview` 一个端点支撑（已补）。它一次返回标量 + 分组，
> 前端不做聚合 —— 「拉 300 条自己算」是把代价从数据库挪到每个人的浏览器，
> 而且 `limit` 一满就静默算错。

### 4.2 需求工作台 `/requirements`

| 页面 | 区块 |
|---|---|
| 需求库（列表） | 左：筛选（状态/版本/渠道/输入人/业务域/优先级/风险/时间/能力标签）<br>中：列表（14 字段 + 关系数 + 风险标记）<br>右：详情预览（点开进档案页） |

## 五 与后端的三条约定

重构期间前后端并行，这三条能把返工压到最小：

1. **契约以 `docs/api-contract.md` 为准，不以 OpenAPI 为准**。
   字段名对不上是重写前端最常见的坏法，而它跑起来才炸。契约文档已经记录了
   三次「文档与实现不一致」的实测（ID 序列化、字段数、SSE 事件名）。
   **新增端点必须同步契约**，否则前端照 OpenAPI 写必踩。

2. **游标分页暂不做**。当前全是 `limit` + `{items:[]}`。需求量大起来之后要分页，
   那时是**后端先加**、前端再跟 —— 不要让前端先做出「翻页按钮但后端只返回 100 条」。

3. **错误结构不各自发挥**。401/403/404/409/422 的含义是冻过的（契约 §1.2），
   前端按状态码分支，**不要解析 detail 文本判断类型**（那是中文，会改）。

## 六 工程结构

### 6.1 技术选型（**已定：原生 HTML/CSS/JS + ES Modules，无构建步骤**）

> ⚠️ **本节在 2026-09-18 被推翻过一次，这里保留推翻的过程。**
>
> 原文写的是「已定：React + TypeScript + Vite」，并判断纯静态方案
> 「本方案要的规模下会失控」「**C 不可行**」。**那个结论是错的**，理由有两条：
>
> 1. **约束变了。** 这个仓库的部署形态是「FastAPI 挂一个静态目录」，没有 npm、
>    没有 CI、没有构建产物。引入 Vite 意味着多一条构建链、多一份产物要同步、
>    多一个「改完忘了 build」的失败模式 —— 而维护它的人不一定在前端。
> 2. **§四的界面量被高估了。** 「40+ 页面」是把每个区块都当成独立页面数的结果。
>    按真正的一级入口算是 **8 个模块 + 4 个详情页**，其中一半是「列表 + 详情 + 几个按钮」。
>    表格、Diff、时间线确实是手写，但它们的**形状在本项目里是固定的**
>    （见 §四每张表的区块清单），不需要一个通用组件库去覆盖未知场景。
>
> **原文那句「造得不会有框架好」依然成立** —— 所以本方案不造框架：
> `http.js` / `api.js` / `format.js` 各自只做一件事，没有状态管理、没有路由库、
> 没有虚拟 DOM。页面的「路由」就是 8 个独立 HTML。

| 方案 | 结论 |
|---|---|
| A. React + TypeScript + Vite + TanStack Query | ❌ **与部署形态冲突**（要构建步骤、要 npm） |
| B. Vue 3 + TS + Vite | ❌ 同上 |
| **C. 原生 HTML/CSS/JS + ES Modules** | ✅ **采用** |

**硬约束（实施时不许破）**：

- 不使用 React / Vue / Angular / Vite / Webpack / TypeScript
- 使用原生 ES Modules；**不新增 npm 构建流程**
- 由 FastAPI 提供静态文件与 API

**当前实现与目标迁移的边界**：现有新页面仍位于 `static/app/`，使用
`core.js`、`shell.js` 与页面脚本的全局加载方式；其中 `core.js` 已提供具名 API
的过渡层，但 HTML 尚未以 `type="module"` 加载，也没有 `static/assets/` 目录。
本节的 ES Modules 与目录拆分是已确定的**下一步目标**，不应被表述为既成事实。
迁移按页面进行：先让一个页面在新公共层下行为等价，再迁移下一个；迁移期间不得重写
已经工作的审核、需求档案或深链接行为。

**代价如实写下来**（这些是真的会遇到的）：

- 关系图、Diff 视图、时间线要手写 —— 这是选 C 的主要成本，无法回避
- 没有类型系统，字段名写错要到运行时才发现 —— 缓解办法是
  `docs/refactoring/frontend-api-mapping.md` 的那张字段表**逐条照抄**，
  以及 `scripts/verify_api_contract.py` 在服务端兜底
- 「组件复用」靠纪律而非工具：`static/assets/js/components/` 里不认识业务

### 6.2 目标目录与路由（2026-09-18 定稿）

下列是迁移完成后的目标目录，**不是当前磁盘结构**。当前已交付页面继续从
`static/app/` 提供；只有在对应页面迁移并验证完成后，才创建并切换到下列文件。

```
static/
├── index.html          # 旧前端，保留不动（§6.3）
├── css/ js/            # 旧前端，保留不动
├── app/                # 当前工作台实现（core.js、shell.js、页面脚本），逐页迁移来源
├── assets/             # 新增：新工作台公用层
│   ├── css/
│   │   ├── base.css        变量、reset、排版
│   │   ├── layout.css      左侧导航 + 顶栏 + 页面骨架
│   │   ├── components.css  按钮/卡片/徽章/表格/抽屉/三态
│   │   └── pages.css       页面级微调
│   └── js/
│       ├── http.js         **所有 HTTP 请求的唯一出口**（鉴权头、状态码分支）
│       ├── api.js          **所有端点的唯一出口**（一个端点一个具名函数）
│       ├── state.js        筛选条件、当前页参数
│       ├── layout.js       导航 + 顶栏
│       ├── format.js       时间/数字/文本格式化
│       ├── escape.js       DOM 构建（`textContent`，全程不碰 innerHTML）
│       ├── chat.js         对话助手（全局可唤起）
│       ├── components/     无业务语义的通用件
│       └── pages/          一页一个文件，只做「取数 + 编排区块」
├── requirements/       index.html · detail.html
├── intake/             index.html
├── analysis/           index.html · run.html
├── reviews/            index.html · detail.html
├── versions/           index.html
├── knowledge/          index.html
└── ops/                index.html
```

**URL 与目录的关系**：目录按模块分层，但 **URL 统一挂在 `/app/*` 下** ——
`static/reviews/detail.html` 对应 `/app/reviews/detail`。

这样选的理由：`/app/` 前缀**已经在 `api/auth.py` 的豁免清单里**（页面本身要能打开，
数据请求仍要 token），鉴权接线一行不用改。深链接由 `api/app.py` 中的**显式安全路由**
提供，例如 `/app/reviews/detail`、`/app/requirements/{key}` 和
`/app/analysis/runs/{id}`；不接受任意嵌套路径，也不根据 URL 拼接静态文件路径。

**关键约定**：

- `pages/` **不直接 fetch**，也不出现字面量路径 —— 一律调 `api.js` 里的具名函数。
- `components/` **不认识业务**。它们收数据、返 DOM，不知道什么是需求。
- **权限要提前灰掉**：`403` 不是「点了才报错」，是**灰掉并说明缺哪一档**。
  但**灰按钮不是安全边界** —— 判定永远在后端（§八）。
- **`http.js` 是唯一出口**：任何绕过它的 `fetch` 都是那个页面 401 的原因。

### 6.3 与旧前端的并存

新工作台挂 `/app/*`，旧的 `/ui` 保持不变。**逐个页面替换**，替换完一个才删一个。
后端静态挂载同时服务两边，不存在切换时刻。

## 八 明确不做

- **不做「影响分析」的替代品**。B4 未完成前，关系列表**不是**影响分析 ——
  前者是「已知的边」，后者是「改动会波及哪些」（要依赖传播 + 环检测）。
  界面上把它标成「未提供」比拿关系列表充数诚实。
- **不做前端编排的多步写操作**。审核通过 + 合并 + 回滚各有事务边界，
  前端只调一个端点，不做「先 A 后 B、失败回滚」。
- **不做离线/本地缓存**。内部工作台，无此需求。
- **不做移动端适配**。信息密度决定它是桌面工具。
- **不在前端做权限判断的业务逻辑**。「谁能回滚」由后端 403 说了算，
  前端只是**提前灰掉**（体验），不是**安全边界**。
