# 方案：前端工作台重构

> 依据 `docs/Requirement_agent后端任务与前端重构规划.docx` §五～§十。
> 本文只做**界面规划与实施路径**，不重复后端批次（B 系列）的设计。
>
> **前置事实（2026-09-17 实测）**：后端还有 **6 个端点不存在**，会直接卡住若干界面。
> 见 §三 —— 那张表决定「哪些页面现在能开工」。

---

## 一 现状：为什么不能只是「加几个页面」

当前前端（`static/`，**无构建步骤，纯静态**）：

```
index.html  160 行   app.js 1997 行   styles.css 510 行
布局：左栏会话列表 │ 中间对话 │ 右栏工作台
右栏 5 个 tab：待办 / 需求库 / 文档库 / 审计 / 运维
右下角浮层：需求库大表（筛选 + 导出）
```

**它是「对话为中心，工作台是附属」。** 而规划文档要的是反过来：
**治理工作台为中心，对话是其中一项能力**。

这不是加页面能解决的，有三个结构性问题：

| 问题 | 表现 | 为什么现在改比以后改便宜 |
|---|---|---|
| **没有路由** | 所有状态在一个页面里，靠 `state.sessionId` 与 tab 切换；**没法把「这条需求的审核页」发给人** | 加路由要拆掉全部 `renderXxx()` 的隐式依赖 |
| **没有数据层** | 31 处 `apiJson` 散在各处，各自处理加载/错误/刷新；同一个端点在不同地方被重复拉 | 引入统一的请求层与缓存是重构的地基 |
| **1997 行单文件** | 需求库、审核、版本、运维、对话全在一个文件里 | 拆文件必须先定边界，而边界就是本方案 §四 |

> ⚠️ **不要「渐进式改这个 app.js」**。它的组织方式是「一个页面 + 一堆渲染函数」，
> 在这个结构上叠加 8 个模块，只会得到一个 5000 行的文件。
> 正确的渐进是**并存**：新工作台另起，逐个页面替换，旧页面最后删（§七）。

## 二 目标与边界

**目标**：把「需求表格 + 详情 + 几个按钮」升级为需求治理工作台 ——
围绕**需求输入、分析、审核、版本、来源、运行状态**组织信息。

**边界**（沿用后端批次的原则）：

- **前端不反向决定后端事务边界**：审核通过、合并、回滚都只调既有端点，
  前端不做「先改 A 再改 B」的编排（那是后端事务的事）。
- **不引入后端没有的能力**：界面上出现的每个数都要有端点支撑；
  没有的数据**显示「未提供」而不是编一个 0**。
- **权限如实呈现**：`403` 说明角色不够，界面应当**灰掉**对应操作并说明原因，
  而不是让人点了才报错。

## 四 信息架构

规划文档给的一级导航照搬，但**每个模块下面的页面要落到可执行的粒度**。

```
总览            /
需求工作台      /requirements
输入中心        /intake
智能分析        /analysis
审核中心        /reviews
版本与变更      /versions
来源与知识      /knowledge
系统运维        /ops
```

对话助手**不再占一个一级入口** —— 它是「随时可唤起的能力」（全局按钮 / 侧滑），
而不是一个要主动切过去的页面。这是与现状最大的差别。

### 4.1 总览 `/`

| 页面 | 区块 | 数据 |
|---|---|---|
| Dashboard | 待我处理（待审数、冲突数、高风险数、死信数） | 聚合 |
| | 系统健康（DB / LLM / Embedding / **向量来源**） | 3 个 health 端点 |
| | 近期活动（最近提交、最近审核、最近失败） | 聚合 |
| 趋势与分布 | 需求提交趋势（按周/月） | 聚合 |
| | 渠道占比、领域分布 | 聚合 |
| 风险与漏斗 | 风险矩阵（质量×变更） | 聚合 |
| | 审核漏斗（提交→待审→通过/拒绝） | 聚合 |

> ⚠️ **整块依赖一个还不存在的聚合端点**（缺口 #1）。没有它，这一屏只能靠
> 「拉 300 条需求前端自己算」—— 那是把聚合的代价从数据库挪到每个人的浏览器，
> 数据量一上来就废。

### 4.2 需求工作台 `/requirements`

| 页面 | 区块 |
|---|---|
| 需求库（列表） | 左：筛选（状态/版本/渠道/输入人/业务域/优先级/风险/时间/能力标签）<br>中：列表（14 字段 + 关系数 + 风险标记）<br>右：详情预览（点开进档案页） |
| 需求档案 `/requirements/:key` | ① 概览（编号/名称/状态/当前版本/负责人）<br>② **最终需求描述**（可展开看来源、看原文、看新增与被覆盖）<br>③ 来源链（哪几条来源合成它）<br>④ 关系与影响（关系列表 + **影响范围**）<br>⑤ 版本时间线<br>⑥ Agent 分析结果（候选/判定级别/理由/是否降级） |
| 关系图（档案页内） | 以当前需求为中心的邻域图；**边带类型与状态**（proposed/confirmed） |

> 「影响范围」区块**在 B4 完成前没有数据**（缺口 #7）。先按「未提供」占位，
> 不要拿关系列表假装是影响分析 —— 那两件事不一样（见 §八）。

### 4.3 输入中心 `/intake`

| 页面 | 区块 |
|---|---|
| 文本提交 | 富文本 + 渠道/提交人/业务域 |
| 文件导入 | 拖拽多文件 → `POST /requirements/ingest` |
| 渠道接入 | 飞书 webhook 状态（**无端点，见缺口**）、签名配置说明 |
| 导入任务 | 提交后的来源 → 分析进度（received → pending_review） |

### 4.4 智能分析 `/analysis`

| 页面 | 区块 |
|---|---|
| 分析任务列表 | 全部 Agent Run（时间/触发来源/状态/耗时）—— 缺全量列表端点 |
| Run 详情 `/analysis/runs/:runId` | **节点时间线**（可展开：输入摘要、工具参数、输出、耗时）<br>工具调用表（名称/参数/耗时/结果条数/错误）<br>模型调用表（provider/model/task_type/tokens/延迟/是否降级）<br>最终结果 |
| 检索判定（Run 内） | 候选列表 + 余弦 + relevance/contrast + 判定级别 + **未召回 vs 模型否定** |
| 冲突 / 风险视图 | 按冲突类型、风险等级聚合看 |

> Run 详情的数据**已经齐了**（B2.1 + B3.1），这是最值得先做的「新能力」页面 ——
> 它把「模型怎么得出这个结论」第一次变得可看。

### 4.5 审核中心 `/reviews`

| 页面 | 区块 |
|---|---|
| 待审队列 | 左：队列（按提交时间/风险/冲突排序）<br>右：审核工作区 |
| 审核工作区 | ① 原始输入（原文/文件/渠道）<br>② 结构化需求<br>③ 相似需求（**带判定级别与降级标记**）<br>④ 冲突、风险<br>⑤ **版本 Diff**（若合并进既有主线）<br>⑥ **影响范围**（B4 后）<br>⑦ Agent 建议<br>底部操作：通过 / 拒绝 / 退回 / 标记冲突 / 合并 |
| 合并预演 | `merge-preview` 的分组增删改 + **warnings 必须显示**（删除清单只在这里喊） |
| 审核历史 | 已审列表（缺口 #3） |

### 4.6 版本与变更 `/versions`

| 页面 | 区块 |
|---|---|
| 时间线 | Git 式版本链；**用 `status === 'current'` 判当前版，不要假设 version_no 最大** |
| Diff | 版本间功能级增删改（`modified` 已不恒空） |
| 合并 / 回滚 | Revert **必须显示目标版本、影响版本、关联需求、所需权限、确认信息**，不能做成快捷按钮 |

### 4.7 来源与知识 `/knowledge`

| 页面 | 区块 |
|---|---|
| 来源中心 | 来源列表（类型/输入人/时间/解析状态/分析状态/关联需求/失败原因/重试入口）—— 缺列表端点 |
| 原始文件 | 文档库 + 分片 + 检索 |
| 文档版本链 | 同一文件的多个版本 |
| 能力与条件 | 能力词表、条件词表、`feature_capability` 裁决 |

### 4.8 系统运维 `/ops`

| 页面 | 区块 |
|---|---|
| 系统健康 | DB / LLM / Embedding / **向量来源**（`/health/embedding` 的 stale/unknown） |
| 任务队列 | Outbox 按状态计数 + 列表 |
| 死信 | 列表 + 重投 / 丢弃 |
| Worker | 心跳、消费统计 —— 缺端点 |
| 模型 | 调用记录（provider/model/task_type/tokens/延迟/降级）+ 路由配置诊断 |
| 渠道 | 状态 —— 缺端点 |
| 审计 | 事件流（含 `before/after` 数据） |
| 对话与记忆 | 会话列表、长期记忆 |

## 五 与后端的三条约定

重构期间前后端并行，这三条能把返工压到最小：

1. **契约以 `docs/api-contract.md` 为准，不以 OpenAPI 为准**。
   字段名对不上是重写前端最常见的坏法，而它跑起来才炸。契约文档已经记录了
   三次「文档与实现不一致」的实测（ID 序列化、字段数、SSE 事件名）。
   **新增端点必须同步契约**，否则前端照 OpenAPI 写必踩。

2. **游标分页暂不做**。当前全是 `limit` + `{items:[]}`。需求量大起来之后要分页，
   那时是**后端先加**、前端再跟 —— 不要让前端先做出「翻页按钮但后端只返回 100 条」。

3. **错误结构不各自发挥**。401/403/404/409/422 的含义是冻过的（契约 §1.2），
   前端按状态码分支，**不要解析 detail 文本判断类型**（那是中文，会改）。

## 六 工程结构

### 6.1 技术选型（**这一条需要你定**）

| 方案 | 适合 | 代价 |
|---|---|---|
| **A. React + TypeScript + Vite + TanStack Query**（推荐） | 8 模块、40+ 页面、大量表格/表单/Diff/图 | 需要构建步骤；团队要会 React |
| B. Vue 3 + TS + Vite | 同上，团队更熟 Vue 时 | 同上 |
| C. 继续纯静态（vanilla） | 页面少、不想引入构建 | **本方案要的规模下会失控** —— 关系图、Diff、时间线都要手写 |

选 A/B 的决定因素**不是技术，是你们团队维护哪一套更顺手** —— 这是长期要有人改的东西。

> 我的判断：按 §四 的界面量，**C 不可行**。40+ 页面的状态管理、路由、
> 数据缓存、表单校验，手写一遍等于自己造半个框架，而且造得不会有框架好。

### 6.2 目录（规划文档 §八 照搬，补上落点）

```
web/
  app/            路由表、全局布局（左侧导航 + 顶栏）、Provider
    routes.tsx    一级导航 → 页面的映射
    layout/       Shell、NavRail、TopBar
  pages/          一页一个目录，只做「取数 + 编排区块」
    overview/ requirements/ intake/ analysis/
    reviews/ versions/ knowledge/ ops/
  features/       业务模块（跨页面复用）
    requirement/ review/ version/ relation/ risk/ agent-run/
  components/     无业务语义的通用件
    DiffView/ Timeline/ RiskMatrix/ RelationGraph/ EventStream/
    DataTable/ FilterBar/ EmptyState/ ErrorState/ PermissionGate/
  services/       按领域封装的 API 调用（每个端点一个函数 + 类型）
  stores/         筛选条件、会话、运行状态
  types/          API 响应类型（**从契约文档生成或手抄，不靠猜**）
```

**关键约定**：

- `pages/` **不直接 fetch**，只做「取数 + 编排」；请求走 `services/`。
- `components/` **不认识业务**。`RelationGraph` 收 nodes/edges，不知道什么是需求。
- **`PermissionGate` 是组件**：`403` 不是「点了才报错」，是**灰掉并说明缺哪一档**。

### 6.3 与旧前端的并存

新工作台挂 `/app/*`，旧的 `/ui` 保持不变。**逐个页面替换**，替换完一个才删一个。
后端静态挂载同时服务两边，不存在切换时刻。

## 七 分期（按**后端就绪度**分批，不是按模块）

这是本方案与规划文档 §十 最大的差别：**不按模块做，按「后端给不给数据」做**。
否则做完一屏发现没数据，或者数据形状还会变。

| 批次 | 内容 | 前置 | 为什么排这里 |
|---|---|---|---|
| **F0** | 拆地基：路由、布局、请求层、`services/`（先只包**已有**端点）、类型 | 无 | 地基不先做，后面每页都要重来 |
| **F1** | **审核中心全量**（队列 / 工作区 / 合并预演）+ **版本与变更全量** | F0 | 这两块**后端 100% 就绪**，且是日常最高频的工作 |
| **F2** | **需求工作台**（库 / 档案 / 关系图） | F0 | 同样就绪；「影响范围」区块先占位 |
| **F3** | **智能分析**（Run 列表 / Run 详情 / 检索判定） | F0 + 缺口 #6 | 后端新能力（B2.1/B3.1）的第一次可视化，价值最高 |
| **F4** | **系统运维**（健康 / 队列 / 死信 / 审计 / 模型调用） | F0 + 缺口 #4 #5 | 缺口小，但运维页是排障时才用 |
| **F5** | **总览 Dashboard** | 缺口 #1 | 整块卡在聚合端点 |
| **F6** | **来源与知识**（来源列表 / 文档 / 能力词表） | 缺口 #2 | |
| **F7** | **输入中心** | 缺口（截图、任务进度） | 多数能力已有，但「导入任务进度」缺端点 |
| **F8** | 对话助手并入（全局可唤起） | 全部 | 放最后，因为它现在是可用的，动了反而打断使用 |

**F0～F2 现在就能开工**（后端已就绪）。F3～F8 各卡一个缺口，见 §三 的清单。

## 八 明确不做

- **不做「影响分析」的替代品**。B4 未完成前，关系列表**不是**影响分析 ——
  前者是「已知的边」，后者是「改动会波及哪些」（要依赖传播 + 环检测）。
  界面上把它标成「未提供」比拿关系列表充数诚实。
- **不做前端编排的多步写操作**。审核通过 + 合并 + 回滚各有事务边界，
  前端只调一个端点，不做「先 A 后 B、失败回滚」。
- **不做离线/本地缓存**。内部工作台，无此需求。
- **不做移动端适配**。信息密度决定它是桌面工具。
- **不在前端做权限判断的业务逻辑**。「谁能回滚」由后端 403 说了算，
  前端只是**提前灰掉**（体验），不是**安全边界**。
