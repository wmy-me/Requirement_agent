# 方案：文档同名同格式的版本链 —— 现状分析与实施方案

> 状态：**待确认**。本文只做分析与设计，**不含代码改动**。
> 写于 2026-09-15。现有数据量：`document_asset` 1 行 / `document_chunk` 6 行。

---

## 0. 三句话结论

1. **文档侧现在没有「版本」这个概念。** 一份 PDF 改一个字，库里会多出一份**互不相干的
   新资产** —— 不是同一份文档的 v2。所以「同名同格式的文档更新」这条路径**根本不成立**。
2. **要做的不是加一个 `version_no` 列，而是把文档身份从「内容」改成「名字 + 格式」。**
   这是**和需求侧能力模型同量级**的改造，不是小修补。
3. **但其中一块可以白捡**：`document_chunk` 用 `chunk_index`（位置）当身份，
   与 E 批刚修掉的 `requirement_feature` 那个 bug **同源**——修法可以直接复用
   `domain/feature_diff.py` 的匹配内核。

## 1. 现状

### 1.1 两张表

| 表 | 列 | 关键点 |
|---|---|---|
| `document_asset` | `id, file_name, content_type, storage_uri, checksum, size_bytes, source_type, source_id, original_text, extracted_text, metadata, created_at, updated_at` | **无任何版本列**；身份 = `checksum` |
| `document_chunk` | `id, document_id, chunk_index, chunk_text, embedding(vector 4096), metadata` | **`UNIQUE (document_id, chunk_index)`** —— 位置即身份；**无 `content_hash`** |

### 1.2 现在的去重规则（`repositories/document.py:39`）

> 「按内容校验和去重：checksum 相同的文件视为同一份资产，直接返回既有行。」

### 1.3 与「同名同格式才更新」的差距

| 场景 | 你要的 | 现状 |
|---|---|---|
| 同名同格式，内容**改了一个字** | 更新 → 产出新版本 | ❌ **新建一份新资产**（checksum 变了） |
| 同名同格式，内容完全一样 | 更新？ | 复用既有行 |
| 不同名，内容一样 | 新建 | 复用既有行（去重） |

**所以现状永远不会因为「同名同格式」而更新**，改一个字就变成两份互不相干的文档。

### 1.4 上传路径

| 入口 | 位置 |
|---|---|
| 需求附件上传 | `api/routes/requirements_write.py:202`（`document_repo.save`） |
| 对话文件上传 | `api/routes/agent_chat.py:550` |
| 切片与向量 | `infrastructure/worker/tasks.py::DocumentChunkingTask`（走 outbox 异步） |

## 2. 三个卡点

### 卡点一：`document_asset` 没有版本链（**最根本**）

文档身份是**内容哈希**，不是「名字 + 格式」。所以：

- 内容一变 → 新身份 → 新资产，与旧的**没有任何关联**
- 想表达「这是同一份文档的新版本」，**库里没有地方装**

### 卡点二：`document_chunk` 用位置当身份

`UNIQUE (document_id, chunk_index)` 意味着分片靠**序号**认身份。改一个字如果让分片
边界移动，**后面所有 `chunk_index` 都会错位**。

> **这和 E 批修掉的 `requirement_feature` bug 是同一个形状** —— 那时也是用 ordinal
> 位置当身份，插一行就把它后面全判成 `modify` 并真实覆写 `content_hash`。
> E 批的修法（内容哈希匹配 + 保序 + 纯函数内核）**可以照搬**。

### 卡点三：分片没有 `content_hash`，**没法判断「哪个变了」**

要做「改一个字只更新那一个 chunk」，第一步得知道**是哪个 chunk 变了**。
现在只有 `chunk_text` 和 `embedding`，无从比对。

## 3. 建议的表与字段（草案）

### 3.1 `document_asset` 加版本链

**推荐做法：拆成「文档主线 + 文档版本」两张表**，照搬需求侧
`requirement_master` / `requirement_version` 已经验证过的形状：

```sql
-- 文档主线：身份 = (file_name, content_type)
CREATE TABLE document_stream (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    file_name    TEXT NOT NULL,
    content_type TEXT NOT NULL,
    current_version_no INTEGER NOT NULL DEFAULT 0,
    status       TEXT NOT NULL DEFAULT 'active'
                 CHECK (status IN ('active', 'archived', 'deleted')),
    created_at, updated_at
);
-- 同一 (名字, 格式) 只留一条主线 —— 这正是「同名同格式才更新」的落点
CREATE UNIQUE INDEX uq_document_stream_name_type
    ON document_stream (file_name, content_type);
```

```sql
-- 文档版本：每版一行，内容仍是原来的 document_asset 那套字段
ALTER TABLE document_asset
    ADD COLUMN stream_id BIGINT REFERENCES document_stream(id),
    ADD COLUMN version_no INTEGER,
    ADD COLUMN status TEXT NOT NULL DEFAULT 'current'
        CHECK (status IN ('current', 'superseded')),
    ADD COLUMN superseded_by_version_no INTEGER;

CREATE UNIQUE INDEX uq_document_version ON document_asset (stream_id, version_no);
-- 同主线只有一个 current —— 与 requirement_version 用同一招（部分唯一索引）
CREATE UNIQUE INDEX uq_document_current
    ON document_asset (stream_id) WHERE status = 'current';
```

> ⚠️ **`supersede_current` 必须先于插入调用**。需求侧批次 3 在这里踩过：
> 数据库的部分唯一索引不允许两个 `current`，而插入时默认就是 `current` ——
> 顺序反过来会**在第二条版本上撞唯一约束**（第一条一切正常、第二条才炸）。

### 3.2 `document_chunk` 加内容哈希

```sql
ALTER TABLE document_chunk
    ADD COLUMN content_hash TEXT;
CREATE INDEX idx_document_chunk_hash ON document_chunk (document_id, content_hash);
```

**`UNIQUE (document_id, chunk_index)` 保留但降级**：它仍然保证「同一版本内序号不重复」，
但**匹配身份改用 `content_hash`**（照 E 批的做法）。

### 3.3 写入改为「按内容 diff」

```
新上传 → 定位或新建 document_stream（同名同格式）
      → 切分得到新分片列表
      → plan_chunk_sync(现有分片, 新分片)  ← 复用 feature_diff 的内核
      → 变了的：重新 embedding
      → 没变的：复用既有行与其向量（**省掉的就是这一块**）
      → 删掉的：软删
```

**「改一个字只更新一个 chunk」的收益正在这里**：不必重算整篇文档 4096 维向量。

## 4. 旧数据迁移

现有 1 个资产 / 6 个分片，**量极小**，但仍要按「历史不能丢」处理。

| 步骤 | 内容 |
|---|---|
| 1 | 加列（全部带默认值、可空），建 `document_stream` |
| 2 | **回填**：每个既有 `document_asset` 各建一条 `document_stream`（用它的 `file_name`/`content_type`），自己成为 v1 / `current` |
| 3 | 回填 `document_chunk.content_hash`（从 `chunk_text` 现算，口径与 `feature_diff` 一致） |
| 4 | **不回溯合并**：同名同格式的历史资产**不自动合并成版本链** —— 那是编造历史。真要合，人工在 UI 上做 |

> 第 4 步借鉴能力模型批次 3 的判断：历史版本的能力快照**留空**而不是硬造一份，
> 「空着比编一个更干净」。

**回滚**：全是 `ADD COLUMN` / `CREATE TABLE`，回滚只需 `DROP` 新对象。

## 5. 分批实施

| 批 | 内容 | 破坏性 | 验证 |
|---|---|---|---|
| **1** | `document_stream` + `document_asset` 版本列 + **回填**（每份既有资产各成 v1） | 无（纯新增） | 既有 1 份资产能查到 stream 且是 current |
| **2** | `document_chunk.content_hash` + **纯函数 `plan_chunk_sync`**（复用 `feature_diff` 的内核） | 无 | 单测：中间插入一片 → 只有 1 条 add，其余全 keep |
| **3** | 写入路径改为「定位/新建 stream → diff → 只重算变化的分片」 | **有**（改上传路径） | 同名同格式改一个字 → 产出 v2，且**只有变化的 chunk 被重算** |
| **4** | 只读查询与展示（文档版本历史、分片 diff） | 无 | 真实数据走查 |
| **5** | 旧数据回填 + 验收 | 无 | 回填报告 |

**批次 1–2 全程不碰现有写入路径**，可以随时停。有风险的是批次 3。

## 6. 兼容性风险

| # | 风险 | 对策 |
|---|---|---|
| 1 | **身份定义变了**（checksum → 名字+格式），可能让原本被去重挡住的重复上传**产生新版本** | 迁移时先回填全部既有资产为 v1；批次 3 上线前用真实重复上传场景走查 |
| 2 | `document_asset` 被**两个入口**调用（需求附件、对话文件），改一处漏一处 | 两处都改，且用同一份「定位/新建 stream」的服务方法 |
| 3 | 分片重算会触发 embedding 调用；**改错会放大成本** | 批次 3 的验证必须包含「未变化的 chunk 确实复用、没有重新 embedding」 |
| 4 | `document_chunk.embedding` 是 4096 维、`006` 曾删过 HNSW 索引 | 本方案**不动向量维度与索引**，只动匹配方式 |
| 5 | 同名文件但**格式不同**（`报告.pdf` vs `报告.txt`）按设计是两条主线 | 符合你的规则，但要在 UI 上让人看得懂 |

## 7. 待你拍板

**① 拆两张表，还是在 `document_asset` 上加版本列？**

我推荐**拆**（`document_stream` + 版本行）——理由是与需求侧 `requirement_master` /
`requirement_version` 形状一致，接手的人不用学第二套；而且「同名同格式」这条唯一性
约束天然落在 stream 上。代价是多一次 JOIN。

**② 「同名同格式」的判定要不要规范化？**

`报告.pdf` 与 `报告.PDF`、`报告 v2.pdf` 与 `报告.pdf` 算不算同名？我倾向
**先做精确匹配**（大小写敏感、不做版本号剥离），把它作为已知限制 —— 规范化规则
一旦做错，会把两份不同文档合成一条主线。

**③ 文件本身要不要留存历史版本？**

`storage_uri` 指向 object storage。产出版本时，**旧版本的原件要不要保留**？
保留则存储成本随版本数线性增长；不保留则「v1 的文件」只剩文本快照。
我倾向**保留**（对象存储便宜，而「原件」是不可再生的事实）。

**④ 分片 diff 的粒度**

按 `content_hash` 精确匹配 —— 那**改一个字会让它所在的那个 chunk 变成 add + delete**
（而不是 modify）。要展示成「修改」需要额外的相似度判断。我倾向**先精确匹配**，
把「改一个字」表现为「删一片 + 加一片」，不做模糊匹配。
