## 0. 三句话结论

1. **你要的东西，现有系统满足约六成**：`requirement_master` 就是「需求主线」，`requirement_version` 就是「版本时间轴」，`requirement_version_source` 就是「来源记录」，且**每个版本已经保存了完整快照**（`requirement_snapshot`）。所以**不需要新建这几张表**——你的改造原则第 3 条（优先复用）和第 10 条（不重复建概念相同的表）都指向「扩展」。
2. **真正缺的是两样：能力（Capability）和条件（Constraint）**，且两者都不存在（全库零命中）。这才是本次要新增的东西。
3. **但你的表设计有三处结构问题**（§9）：`capability_id` 单列装不下多能力需求（§9-2）、

   **正交**，不新建 module 表，批次 3 因此更小）。前两条仍待确认。
4. **Agent 的职责边界已由 §11 钉死**：Agent 只做分析、归类、推荐、预处理；
   凡改变正式需求、版本历史、受控词表或需求关系的操作**必须人工确认**。
   这条是本次改造最容易做错的地方，已落成代码约束（见 §12.3）。

## 3. 建议的表与字段（**含需要你先拍板的部分**）

> **状态标注**：§3.1 已在**批次 1 落地**（`migrations/015`，见 §12）；
> §3.2 / §3.3 仍是草案，等 §9-2 / §9-3 确认后进批次 3。
>
> ⚠️ 注意 §3.1 的 DDL 是**设计时的初稿**，实际落地有两处差别：
> `capability.status` / `constraint_vocab.status` 增加了 `pending_confirmation` 取值
> （默认为它，而非 `active`），另建了 `constraint_alias` 表。以 `migrations/015` 为准。

### 3.1 新增：能力与条件的受控词表

```sql
-- 能力：(动作, 对象) 二元组。跨需求稳定，用于搜索/分类/统计。
CREATE TABLE capability (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    action       TEXT NOT NULL,              -- 受控动作词，如「导出」
    object       TEXT NOT NULL,              -- 宾语，如「Excel」
    display_name TEXT NOT NULL,              -- 展示名，如「导出 Excel」
    status       TEXT NOT NULL DEFAULT 'active'
                 CHECK (status IN ('active','deprecated')),
    created_by   TEXT NOT NULL DEFAULT 'analysis',
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE UNIQUE INDEX uq_capability_action_object ON capability (action, object);

-- 限定条件：受控词表。AI 只能「选择」，不能自由创建正式条件。
CREATE TABLE constraint_vocab (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    constraint_key TEXT NOT NULL UNIQUE,     -- 如「按部门筛选」
    display_name TEXT NOT NULL,
    status       TEXT NOT NULL DEFAULT 'active'
                 CHECK (status IN ('active','deprecated','pending_confirmation')),
    created_by   TEXT NOT NULL DEFAULT 'analysis',
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

**为什么能力用 `(action, object)` 两列而不是一个字符串**：这是本次设计的关键。归并时用**精确匹配二元组**，而不是相似度阈值——避免了「按部门筛选导出 Excel」和「导出 Excel」被向量当成同一件事（它们相似度会到 0.85+，必然误合）。

### 3.2 新增：功能条目 ↔ 能力

```sql
-- 一条 feature 可以对应多个能力（§9-2：能力挂 feature 的 N:M，而非 stream 上的单列）
CREATE TABLE feature_capability (
    feature_id    BIGINT NOT NULL REFERENCES requirement_feature(id) ON DELETE CASCADE,
    capability_id BIGINT NOT NULL REFERENCES capability(id),
    raw_text      TEXT NOT NULL,        -- 该 feature 里支撑这个能力的原话
    confidence    NUMERIC(5,4),
    review_status TEXT NOT NULL DEFAULT 'proposed'
                  CHECK (review_status IN ('proposed','confirmed','dismissed')),
    PRIMARY KEY (feature_id, capability_id)
);
```

**关联挂在 `requirement_feature` 上（而不是 REQ 上）是本方案的核心决定**，理由：feature 已经有一整套生命周期（`status` / `origin_version_no` / `removed_version_no`）。需求更新后不再支持某能力 → 该 feature 被软删 → **能力关联自动失效，不需要任何新代码**。这正好回答了你说的「不支持 pdf 导出了，也能把来源删掉」。

### 3.3 新增：条件的受控匹配与待确认

```sql
-- AI 抽出的原始条件 → 若匹配不上词表，进这里待人工确认
CREATE TABLE constraint_candidate (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    raw_constraint TEXT NOT NULL,
    suggested_key  TEXT,
    capability_id  BIGINT REFERENCES capability(id),
    source_id      BIGINT REFERENCES requirement_source(id) ON DELETE CASCADE,
    status         TEXT NOT NULL DEFAULT 'pending_confirmation'
                   CHECK (status IN ('pending_confirmation','accepted','rejected')),
    created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### 3.4 扩展：`requirement_master`（= 需求主线）

```sql
ALTER TABLE requirement_master
    ADD COLUMN IF NOT EXISTS stream_title TEXT,          -- 见 §9-8：与 requirement_name 的关系待定
    ADD COLUMN IF NOT EXISTS primary_capability_id BIGINT REFERENCES capability(id);
```

⚠️ **`primary_capability_id` 单列只承载「主能力」**，多能力需求要靠 `feature_capability` 反查（见 §9-2）。

### 3.5 扩展：`requirement_version`（= 版本时间轴）

```sql
ALTER TABLE requirement_version
    ADD COLUMN IF NOT EXISTS capability_snapshot JSONB NOT NULL DEFAULT '[]',  -- 能力快照
    ADD COLUMN IF NOT EXISTS constraint_snapshot JSONB NOT NULL DEFAULT '[]',  -- 条件快照
    ADD COLUMN IF NOT EXISTS is_current BOOLEAN NOT NULL DEFAULT FALSE;
```

**快照为什么必须单独存 JSONB，而不是每次从 feature 派生**：因为 `module_key`（或未来的条件词表）是会变的。今天把「按部门筛选」改叫「按部门维度筛选」，所有历史版本的派生结果会**一起变**——历史就被污染了。存快照是把「当时怎么理解的」钉死。

`is_current` 是冗余字段（`master.current_version` 已经能表达），但你的设计里明确要求，且能让「某主线当前版本」的查询免一次 JOIN。**注意它需要一个「同 stream 只有一个 true」的保证**，建议用部分唯一索引：
```sql
CREATE UNIQUE INDEX uq_version_current ON requirement_version (requirement_id) WHERE is_current;
```

## 4. 旧数据迁移

现有数据量很小（4 REQ / 5 版本 / 24 feature / 8 source），**迁移风险很低**，但仍要按你的原则「现有需求历史不能丢失」处理。

| 步骤 | 内容 | 是否破坏性 |
|---|---|---|
| 1 | 加列（`ADD COLUMN IF NOT EXISTS`，全部带默认值） | 否 |
| 2 | 建新表（能力 / 条件 / 关联 / 候选） | 否 |
| 3 | ~~回填历史版本的能力/条件快照~~ | **不做**——见下 |
| 4 | 对**当前 active 的 24 条 feature** 跑一次能力抽取，产出 `proposed` 关联 | 否（只新增行） |
| 5 | 人工在审核页逐条确认/驳回能力归属 | 否 |

**第 3 步为什么不回填**：历史版本（v1）当时并没有能力概念，硬造一份「v1 的能力快照」等于**编造历史**。更诚实的做法是快照列留空，并在 UI 上区分「此版本早于能力模型上线，无快照」。

这与你「历史不能被污染」的原则是一致的——**空着比编一个更干净**。

**回滚预案**：所有改动都是 `ADD COLUMN` / `CREATE TABLE`，不删列不改类型。回滚只需 `DROP` 新对象，现有 24 条 feature 与 5 个版本不受影响。

## 5. 新需求进入时，如何判断「新建主线」还是「追加版本」

你的三分支，**现有机制已经实现了其中两条**：

| 分支 | 现有机制 | 状态 |
|---|---|---|
| 追加到已有主线 → 生成新版本 | `review.target_requirement_key` 非空 → `commit_requirement_node` 不新建 master，`version_no = current_version + 1` | ✅ **已实现**（E 批刚打通前端入口） |
| 与已有需求关联，但不修改原需求 | `requirement_relation`（`proposed` 待人工裁决） | ✅ 已实现 |
| 创建新主线 | `target_requirement_key` 为空 → `allocate_key()` 分配 `REQ-{6位}` | ✅ 已实现 |

**所以要补的只有「判断」这一步**——即：分析阶段给出建议「应追加到 REQ-000015」还是「新建」，带置信度，低置信度转人工。这正好落在现有审核页上（和 E 批的合并入口并排）。

判定规则（你的原则 §四.2）：

> **不能仅凭能力名称判断是否属于同一条版本链。**

所以判定输入至少要有：**能力** + **业务对象**（`(动作, 对象)` 里的对象）+ 现有主线的标题/正文。即：

```
新需求：(导出, Excel)，业务对象 = 员工数据
REQ-000002：(导出, Excel)，业务对象 = 员工数据   → 同一业务对象 → 建议追加版本
REQ-000015：(导出, Excel)，业务对象 = 订单数据   → 不同业务对象 → 建议新建主线
```

**这里有个待确认点**：「业务对象」从哪来？现有抽取没有这个字段（只有 `business_domain`，且是 auth/order/report 这种粗粒度领域分类）。见 §9-4。

## 6. 需要改动的 API / Agent / 审核流程

### 6.1 抽取（`skills/prompts.py` + `agents/extract_agent.py`）

现状输出 10 个字段。建议**新增**（不删旧的，符合你的原则 2）：

```
- capability：本条功能的能力，形如 {"action": "导出", "object": "Excel"}
- constraints：限定条件列表，**只能从给定词表里选**，形如 ["按部门筛选"]
- raw_constraint：若条件匹配不上词表，输出原文（进入待确认）
```

并把**现有能力/条件词表**注入 prompt（这一步是防漂移的关键。不给词表让模型自由发挥，必然裂成「导出Excel / Excel导出 / 支持导出Excel」）。

**风险**：现在 prompt 已经在输出 `modules` 了，再加三个字段可能让模型漏字段或乱填。**建议先做一个小实验**（拿现有 24 条 feature 的真实文本跑一遍，看输出稳定性），再决定是否合进同一个 prompt，还是拆成第二次调用。

### 6.2 审核流程（`api/routes/reviews.py` + `commit_nodes.py`）

- 审核页新增一块「**能力归属**」：显示 AI 提议的 `(动作, 对象)` 与条件，人可确认/改选/驳回
- 新增「**主线判定建议**」：建议新建 / 建议追加到 REQ-xxxxx（带置信度）
- `commit_requirement_node` 落库时额外写 `feature_capability` 与版本快照

**注意事务边界**：能力关联必须与 feature 落库**同事务**（现有 `commit_requirement_node` 全程用调用方 session，新写入必须延续这个约定，不要自建 session——`relation.update_status` 就是自建 session 的反例，E 批为此专门加了 `confirm_many(session=...)`）。

### 6.3 只读查询（新增，不破坏现有）

| 端点 | 作用 |
|---|---|
| `GET /capabilities` | 能力词表（供前端下拉、供 prompt 注入） |
| `GET /constraints` | 条件词表 |
| `GET /capabilities/{id}/streams` | 按能力搜需求主线（**你的搜索需求 1**） |
| `GET /capabilities/{id}/streams?constraints=按部门筛选` | 能力 + 条件联合搜（**搜索需求 2**） |
| `GET /requirements/{key}/capabilities` | 某主线的能力与条件 |
| `PATCH /feature-capabilities/{...}` | 人工裁决能力归属 |

**检索现状的限制**：`RetrievalService.search` 的向量分支是**需求级**（`requirement_embedding` 一条 REQ 一条），`search_features` **只有 ILIKE、没有向量**。所以「按能力 + 条件搜」如果走能力表 JOIN，是精确匹配，够用；但如果要「原文兜底」（你的搜索需求 3），feature 级没有向量，只能 ILIKE。**要不要给 feature 加向量，是个成本决策**，见 §9-7。

## 8. 兼容性风险

| # | 风险 | 说明与对策 |
|---|---|---|
| 1 | **prompt 膨胀** | 抽取 prompt 要注入能力/条件词表。词表变大后 prompt 会膨胀，且模型可能开始漏字段。对策：词表只注入**相关**的（按业务域过滤或向量召回 top-N），并在批次 2 实测 |
| 2 | **`business_domain` 语义重叠** | 现有 `business_domain`（auth/order/report…，单值）与新「能力」在概念上有重叠。**建议保留不动**，明确分工：`business_domain` 是粗粒度领域，能力是细粒度功能。不要试图合并 |
| 3 | **`requirement_review` 无索引** | 它没有 `source_id` 索引。能力归属若要关联审核记录，JOIN 会慢。**建议本次顺带补索引**（纯新增，零风险） |
| 4 | **版本表无状态列** | 你的设计要 `status` + `is_current`。现有 `change_type` 是「本版本做了什么变更」，**不是状态**，不要混用 |
| 5 | **`requirement_master.status` 与版本 `is_current` 的职责划分** | `master.status ∈ (active/archived/deleted)` 是主线级；版本级是另一回事。要明确「主线 archived 时其版本 `is_current` 怎么处理」 |
| 6 | **能力抽取会引入新的 LLM 调用成本** | 每次提交多一次调用（或 prompt 变长）。当前 `requirement_embedding` 走 outbox 异步，能力抽取建议也走异步，避免拖慢提交响应（渠道要求 3 秒内应答） |
| 7 | **前端零自动化测试** | 现有前端没有任何测试，改动只能靠浏览器手验。批次 4/5 的验证成本会集中在人工走查上 |

### 9-1 ❗ 「模块」怎么安置？—— **已定：(c) 两个概念保持独立，不新建 module 表**

**原问题**：你的设计图是 `能力 └── 需求主线`（能力在最顶层），但前几轮我们说的是
「模块 → 能力 → 需求」，你最初的需求也是「AI 自动检测出**模块**」。同时现有 D 批已有
`requirement_feature.module_key`（REQ-000015 的「巡检任务模块/问题上报模块/…」）。

**结论（2026-09-15 拍板）**：`模块` 与 `能力` **不是「谁包含谁」，而是两个正交的轴**。
本批**不新建 module 表**，`feature.module_key` 保持现状不动。

**证据 —— 用库里的真实数据看**：

| 模块（`feature.module_key`） | 它下面的功能 | 对应的能力 |
|---|---|---|
| **巡检任务模块** | 创建巡检计划 | (创建, 巡检计划) |
| | 指派任务并推送提醒 | (指派, 任务) |
| | 状态流转 | (流转, 任务状态) |
| | **批量导出巡检计划** | **(导出, 巡检计划)** |
| **统计报表模块** | 统计巡检完成率 | (统计, 巡检完成率) |
| | **导出 Excel 报表** | **(导出, Excel)** |
| | 首页看板 | (展示, 看板) |

- **一个模块里聚合多条能力**（巡检任务模块有 4 条不同能力）
- **同一条动作横跨不同模块**（`导出` 在巡检任务模块是「导出巡检计划」，在统计报表模块是「导出 Excel」）

于是：

> **模块回答「这是需求的哪一部分」；能力回答「这个系统能做什么」。**
> 模块聚合能力，能力出现在多个模块里 —— **谁都不是谁的上级。**

**为什么不建议在能力之上再加模块层**：

1. **原始目标已被能力层实现。** 你最初说「相似的需求放在一个模块中」——在能力模型下，
   相似需求**共享能力**，天然就聚在一起了。模块层不再承担这个职责。
2. **它是第三张受控词表要维护**（能力、条件已两张），而当前数据量是 4 条 REQ / 24 条功能，
   模块层属**过早抽象**。
3. **`feature.module_key` 现在没坏**：它在详情页当 📦 标签用，表达「这条需求内部怎么组织」。

**对批次 3 的影响**：**批次 3 不需要 module 表**，只需 `feature_capability` + 版本快照列，
范围反而更小。

**⚠️ 一条必须记住的限制**：`014` 的注释写着「`module_key` 是**跨 REQ 可复用的稳定标识**
（同名即同模块）」—— **实际做不到**。它是自由文本，第二条巡检需求进来时，模型可能输出
「巡检模块」「巡检任务」「巡检管理」，就裂了。所以：

- 只用于**单条需求内部的展示** → 现状够用，不用动
- 将来要**跨需求按功能域浏览**（「所有涉及巡检的需求」）→ 正确的升级路径是给
  `module_key` 加受控词表（`module` 表 + `feature.module_id`），**而不是在能力上挂分类**

**什么情况下这个决定会改**：如果能给出一个**单靠能力和条件搜不出来的**查询场景，例如
「列出所有『巡检』相关的需求，不管它们是导出、统计还是权限」——那就说明确实需要一个
「功能域」维度，届时再建 module 表。目前已知的三个搜索场景（按能力搜 / 能力+条件搜 /
原文搜）**都能被能力层覆盖**。

### 9-2 ❗ `capability_id` 单列装不下多能力需求

你的 `requirement_streams` 里有单个 `capability_id`。但 **REQ-000015 有 13 条功能、4 个模块**，不可能只有一个能力。

- 如果它表示「**主能力**」→ 语义是什么？谁来选？
- 如果一条主线真的只有一个能力 → 与「一个文档分好多子模块」矛盾

**我建议**：`capability_id` 降级为可空的「主能力」，真实的多对多用 `feature_capability`（§3.2）反查。**请确认。**

### 9-3 ❗ 条件是修饰「哪个能力」的？你的 `version_constraints` 缺一个维度

你写的是 `version_constraints(version_id, constraint_id)`。但用你自己的例子：

> v2：增加按部门筛选

这个「按部门筛选」修饰的是 **「导出员工数据」这个能力**，不是版本里的其它能力。一个版本有多个能力时，`(version_id, constraint_id)` 无法表达「是哪个能力的条件」。

**建议改成三元组** `(version_id, capability_id, constraint_id)`。**请确认。**

### 9-4 「业务对象」从哪来？

你的规则「不能仅凭能力名称判断是否属于同一条版本链」，靠的是**业务对象不同**（员工数据 vs 订单数据）。但现有抽取**没有这个字段**。

- 要新加字段吗？（类似 `capability` 那样抽 `business_object`）
- 还是复用 `requirement_title` / `business_domain`？

**这个是主线判定的核心输入，不定就没法判。请指示。**

### 9-5 能力本身是受控词表吗？

你明确说「AI 不允许直接自由创建**正式条件**」。**但能力呢？** 你没说。

- 如果能力也不许自由创建 → 需要「新增能力申请 → 人工确认」流程，与条件对称
- 如果能力可以自由创建 → 会漂移（导出Excel / Excel导出 / 支持导出Excel）

**我倾向能力和条件一样受控**（都用 `(action, object)` 精确匹配，天然抗漂移），但这会带来「动作词表」的维护成本。**请确认。**

### 9-6 「审核记录」在版本上只能间接到达

你的设计图里「审核记录」挂在版本下。但现有 `requirement_review` 的外键是 **`source_id`**，不是 `version_id`。要拿到「某版本的审核记录」得走 `version → version_source → source → review` **两跳**。

- 接受两跳（不改表）
- 还是给 `requirement_review` 加 `version_id`（需要回填历史）

**请指示。**

### 9-7 要不要给 feature 加向量？

你的搜索需求 3「原文搜索」——现有 `search_features` **只有 ILIKE，没有向量**（向量只有需求级 `requirement_embedding`）。

- 不加 → 搜「按区域层级导出」这类没进词表的表述会漏
- 加 → 新增一张 feature 级向量表 + outbox 任务 + 回填

**成本差异明显，请指示。**

### 9-8 `version_label` 与现有 `version_title` 的关系

你的表里两个都有（`version_no` + `version_label`），现有已有 `version_title`（如「门店巡检管理系统 V1.0 需求」）。

是需要一个**可自定义的展示标签**，还是 `v1/v2/v3` 就够？（后者可以直接由 `version_no` 派生，不必存列。）

### 9-9 关系类型的取值要不要扩？（§11 引入了新名字）

§11.6 里你列的关系类型是 `duplicates_of` / `conflicts_with` / `depends` /
`supersedes` / `merged_from` / `split_from`，而现有 CHECK 约束
（`migrations/009:22`）只有四个：`duplicates_of` / `related` / `conflict` / `depends`。

要定两件事：

1. **`conflicts_with` 与现有 `conflict` 是同一个吗？** 是改名还是并存
   （改名要迁移既有行；并存会出现两个表达同一概念的值）
2. **`supersedes` / `merged_from` / `split_from` 本批是否引入？**
   现有 `relation_type` 的 CHECK 是**表级约束**，加值需迁移。
   注意 F 批（版本链 DAG）可能也要用 `merged_from`，两批要协调，别各自加一次。

**我倾向**：`conflicts_with` 就是现有的 `conflict`（**不改名**，避免无谓迁移与既有数据断裂）；
`supersedes` / `split_from` 等到真有产出方时再加 —— 现在加进去只会是一个没有写入路径的
死枚举（`depends` 已经是这个状态，`009:20-21` 的注释自己承认了）。

## 11. 职责边界：Agent 自动 vs 人工确认（2026-09-15 补充）

> **本节是约束性原则，优先级高于 §3–§7 的具体设计。凡与其冲突，以本节为准。**
> 它回答了「Agent 能做到哪一步就必须停下」——这是本次改造里最容易做错的地方。

### 11.1 总原则

> **Agent 可以自动分析、归类、推荐和预处理；凡是会改变正式需求、版本历史、
> 受控词表或需求关系的操作，必须人工确认。**

Agent 的角色是 **需求分析员 + 版本草稿生成器 + 风险预审员**，**不是最终需求审批人**。

| 谁 | 负责 |
|---|---|
| **Agent 自动** | 抽取、匹配、检索、建议、差异生成、风险初筛 |
| **人工确认** | 主线归属、词表新增、冲突关系、版本提交、驳回、高风险变更 |
| **系统负责** | 事务、版本号、快照、状态流转、审计、并发控制 |

### 11.2 职责边界表

| 环节 | Agent 自动处理 | 是否需要人工 |
|---|---|---|
| 原文抽取 | 提取标题、摘要、能力、条件、功能、业务对象 | 不需要 |
| 能力匹配 | 从已有能力词表中匹配 `(动作, 对象)` | **精确匹配可自动；模糊匹配需人工** |
| 条件匹配 | 从受控条件词表中选择条件 | 精确匹配可自动建议；**新增条件需人工** |
| 相似需求检索 | 找出可能相关的需求主线 | 不需要 |
| **新建/追加判断** | 给出「建议新建」或「建议追加到某主线」 | ❗ **必须人工确认** |
| **重复判断** | 输出重复候选及相似原因 | ❗ **必须人工确认** |
| **冲突判断** | 输出冲突字段、冲突原因、涉及需求 | ❗ **必须人工确认** |
| 风险评估 | 质量、变更、技术影响风险初筛 | 高风险必须人工确认 |
| 版本草稿 | 生成新版本描述、差异、条件快照 | 不需要 |
| **正式生成版本** | 写入 `requirement_version`、更新 current version | ❗ **必须人工确认** |
| 来源关联 | 自动关联原始来源 | 一般不需要 |
| **受控词表新增** | 提议新能力或新条件 | ❗ **必须人工确认** |
| **需求驳回** | 给出驳回建议和原因 | ❗ **必须人工确认** |
| **历史版本修改** | — | ❗ **不允许 Agent 直接修改，必须人工处理** |

### 11.3 三档审核等级（**不要只分「全自动/全人工」**）

**A 级 · 自动归档** —— 只适用于无业务决策的动作：

保存来源 / 保存原文 / 抽取字段 / 生成 embedding / 生成候选 / 记录日志。
**这些是事实记录，不是业务决策。**

**B 级 · Agent 预审，人工一键确认** —— 结构清晰但会影响业务模型的动作：

匹配已有能力 / 匹配已有条件 / 建议追加已有需求主线 / 生成新版本草稿 / 识别低风险变更。

前提（**全部满足**）：能匹配已有词表 ✓ 目标主线明确 ✓ 无冲突 ✓ 无删除功能 ✓ 无高风险字段变化 ✓

**C 级 · 必须人工详细审核** —— 高影响变更：

新增能力 / 新增条件 / 合并需求 / 拆分需求 / 确认冲突 / 删除功能 /
修改权限·数据范围·核心流程 / 跨模块影响 / 高技术风险 / 低置信度判断。

### 11.4 自动处理 vs 进入人工：初始规则集

> **不建议一开始让模型自由决定**，先跑规则。

**可自动处理**：原文保存成功 ✓ 能力精确命中词表 ✓ 条件精确命中词表 ✓ 仅新增普通描述 ✓
无冲突候选 ✓ 无删除功能 ✓ 无权限/数据/接口/安全变更 ✓ 置信度达阈值 ✓

**进入人工审核**：新建主线或追加版本判断不明确 ✓ 能力或条件无法匹配词表 ✓ 涉及多个现有需求 ✓
检测到重复或冲突 ✓ 删除·替换已有功能 ✓ 涉及权限·数据结构·接口·流程 ✓
Agent 置信度不足 ✓ 新版本与当前版本差异过大 ✓

### 11.5 置信度阈值（**辅助，不是唯一依据**）

```
confidence >= 0.95        → 允许自动形成候选（注意：是「候选」，不是正式入库）
0.75 <= confidence < 0.95 → 人工一键确认（B 级）
confidence < 0.75         → 人工详细审核（C 级）
```

> ⚠️ **高置信度只说明模型很确定，不代表模型一定正确。**
> 所以「正式版本提交」**仍然保留人工确认**，不设任何自动通道。

### 11.6 状态流转

**来源（`requirement_source.processing_status`）**：

```
received → extracting → analyzing → candidate_generated → pending_review
                                                             ├── approved → committed
                                                             └── rejected
```

⚠️ 现有 CHECK 枚举（`migrations/001:16`）**没有 `candidate_generated`**，需迁移扩枚举。

**能力 / 条件 / 关系**（`proposed → confirmed / dismissed`，新增条件另有 `pending_confirmation`）：

```
proposed
  ├── confirmed
  ├── dismissed
  └── pending_confirmation
```

**版本（`requirement_version` 需要新增 status 列）**：

```
draft → pending_review → current
```

⚠️ 现有 `requirement_version` **没有 status 列**，且 `change_type`（`new/add/modify/delete`）
是「本版本做了什么变更」，**不是状态**，两者不要混用。

**关系类型**：本节提到了 `duplicates_of` / `conflicts_with` / `depends` / `supersedes` /
`merged_from` / `split_from`。现有 CHECK（`migrations/009:22`）只有
`duplicates_of / related / conflict / depends` ——
`conflicts_with` 是否即现有 `conflict`（改名还是并存）、以及 `supersedes` /
`merged_from` / `split_from` 是否本批引入，**需要确认**（见 §9-9）。

### 11.7 完整流程（Agent 不得绕过的部分）

```
Agent 分析
   ↓
生成能力、条件、主线判定和版本草稿
   ↓
进入 pending_review
   ↓
人工修改或确认
   ↓
ReviewService.submit_decision
   ↓
强事务生成正式版本（commit_requirement_node）
   ↓
更新 current_version
```

**Agent 不得绕过**：`ReviewService` / `commit_requirement_node` / 事务 / 版本号生成 / 并发锁。

> ✅ **这与现有设计一致**——E 批的做法（`proposed` 待人工裁决、`confirm_many` 只由人工合并触发）
> 正是这套原则的既有先例，本次改造延续同一模式，不引入新的自动化通道。

### 12.3 两条关键设计决定（已落地在代码里）

**① 能力归并用精确匹配，不用相似度。**
`(action, object)` 二元组。因为「按部门筛选导出 Excel」与「导出 Excel」的余弦相似度会到

仓储层的强制点。

### 12.4 实施中发现并修复的缺陷

**SQL 运算符优先级陷阱**（由 `test_constraint_create_defaults_to_pending` 抓出）：

`ConstraintVocabRepository.find_exact` 的第一版写成

```sql
WHERE c.constraint_key = :key OR EXISTS (...)      -- 再拼 AND status = 'active'
```

SQL 里 `A OR B AND C` 解析为 `A OR (B AND C)` —— **状态过滤只作用于别名那一支**，
正式键命中的行永远不受约束。后果是 `only_active` 形同虚设，**待确认或已停用的条件
照样能匹配上**，直接破坏了上面第 ② 条边界。

修复：给两个分支整体加括号。已在代码注释里写明为什么这个括号不能省。

> 这条值得记一笔：它正是「先写测试再写实现」的价值 —— 边界类缺陷不会自己暴露，
> 只会安静地让限制失效。

|---|---|---|
| 关联裁决 | `feature_capability.review_status` | **这条需求**有没有这个能力 |
| 能力裁决 | `capability.status` | **这条能力本身**成不成立 |

两者都**只能由人工触发**（方案 §11）。只接受 `confirmed` / `dismissed`，
**不接受改回 `proposed`** —— 撤回裁决要重新分析，与既有的关系裁决端点
（`RequirementRelationUpdateRequest`）同一约定。

### 16.3 端到端验证：完整闭环

```
1) AI 提议能力 (验收动作, 验收对象)  status=pending_confirmation
2) 未确认时匹配   → matched=False          ← 对后续需求而言它等于不存在
3) 人工确认       → HTTP 200  status=active
4) 确认后匹配     → matched=True  id=1     ← 闭环成立
```

**第 2 步是这条边界的实际含义**：「AI 不得自动创建正式能力」不是一句口号 ——
在没人确认之前，AI 提议的能力连参与匹配的资格都没有，所以它污染不了任何结果。

另有测试覆盖：确认后 `find_exact` 能命中、停用后掉出匹配、
别名登记后「按部门维度筛选」能命中正式键「按部门筛选」。

### 17.1 交付物

| 类型 | 内容 |
|---|---|

**为什么不重跑整套抽取**：存量 feature 是在能力模型上线前落库的，它们的
`metadata.extracted` 里没有 `capabilities[]`。重跑全套既贵，**又可能覆盖既有的人工编辑结果**。
按功能正文单独抽能力，是最小侵入的做法。

**靠 `index` 把能力对回 feature，不靠文本匹配** —— 功能正文里可能有重复行。

### 17.2 实施中发现并修复：预演的假象

第一次跑 `--dry-run`，它**建了 11 条能力提案** —— 「预演（不写库）」名不副实，
因为 `CapabilityMatchService.match()` 即使在预演里也会调 `create()`。

**这是最坏的一类 bug**：预演本该是让人放心执行的安全网，它却悄悄改了数据；
而且只有等到真正落库时才会有人发现。修法是给 `match()` 加 `persist` 参数，
`persist=False` 时连提案都不建，只回报「会提议什么」。

**验证**：修复后跑预演，`capability` 表行数前后都是 6，**真的只读**。

### 17.4 回填暴露的一个质量问题（**留给后续**）

REQ-000013 是 2750 字的 PDF 版式文本，它的「功能条目」里有几行**根本不是功能**：

```
V1.0仅包含习惯管理、快速打卡、数据统计、个人中心4个核心模块；不包含好友打卡/分享等社交功能…
性能指标：首页加载≤1.5秒、打卡响应≤200ms、1000人同时在线无明显卡顿
```

回填对它们抽出了这样的「能力」：

```
(创建, 习惯（含名称、每日目标打卡次数、提醒时间、喝水/早睡/运动快捷选项）)
(保障, 性能指标（首页加载≤1.5秒、打卡响应≤200ms…）)
(限定, V1.0功能范围（…；不含社交、商业化…）)
```

**宾语是整句话，动作是「保障/限定/兼容」这类非动作词。**

这不是回填工具的 bug，而是**上游的问题**：那条 feature 本身就不该存在 ——
它是**范围声明/性能指标**，被早期的抽取当成了功能条目，一路直通 `requirement_feature`。

按 §11 的分工，这类噪声会停在 `pending_confirmation`，由人工在审核时驳回，
**不会污染任何正式数据**。但它说明：**功能条目的质量是能力层可信度的上限**。
若要根治，应回到抽取阶段区分「功能条目」与「范围/非功能声明」——属独立议题。
