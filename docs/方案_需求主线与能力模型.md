## 0. 三句话结论

1. **你要的东西，现有系统满足约六成**：`requirement_master` 就是「需求主线」，`requirement_version` 就是「版本时间轴」，`requirement_version_source` 就是「来源记录」，且**每个版本已经保存了完整快照**（`requirement_snapshot`）。所以**不需要新建这几张表**——你的改造原则第 3 条（优先复用）和第 10 条（不重复建概念相同的表）都指向「扩展」。
2. **真正缺的是两样：能力（Capability）和条件（Constraint）**，且两者都不存在（全库零命中）。这才是本次要新增的东西。
3. **但你的表设计有三处结构问题会卡住实现**（§9）：`capability_id` 单列装不下多能力需求、条件缺少「修饰哪个能力」的维度、以及设计图里的「能力」与对话中的「模块」层级对不上。**建议先定这三条再动代码。**

## 3. 建议的表与字段（**含需要你先拍板的部分**）

> 下面的 DDL 是**草案**，`§9` 的歧义未定之前不应落地。

### 3.1 新增：能力与条件的受控词表

```sql
-- 能力：(动作, 对象) 二元组。跨需求稳定，用于搜索/分类/统计。
CREATE TABLE capability (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    action       TEXT NOT NULL,              -- 受控动作词，如「导出」
    object       TEXT NOT NULL,              -- 宾语，如「Excel」
    display_name TEXT NOT NULL,              -- 展示名，如「导出 Excel」
    status       TEXT NOT NULL DEFAULT 'active'
                 CHECK (status IN ('active','deprecated')),
    created_by   TEXT NOT NULL DEFAULT 'analysis',
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE UNIQUE INDEX uq_capability_action_object ON capability (action, object);

-- 限定条件：受控词表。AI 只能「选择」，不能自由创建正式条件。
CREATE TABLE constraint_vocab (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    constraint_key TEXT NOT NULL UNIQUE,     -- 如「按部门筛选」
    display_name TEXT NOT NULL,
    status       TEXT NOT NULL DEFAULT 'active'
                 CHECK (status IN ('active','deprecated','pending_confirmation')),
    created_by   TEXT NOT NULL DEFAULT 'analysis',
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

**为什么能力用 `(action, object)` 两列而不是一个字符串**：这是本次设计的关键。归并时用**精确匹配二元组**，而不是相似度阈值——避免了「按部门筛选导出 Excel」和「导出 Excel」被向量当成同一件事（它们相似度会到 0.85+，必然误合）。

### 3.2 新增：功能条目 ↔ 能力

```sql
-- 一条 feature 可以对应多个能力（见 §9-1 的歧义）
CREATE TABLE feature_capability (
    feature_id    BIGINT NOT NULL REFERENCES requirement_feature(id) ON DELETE CASCADE,
    capability_id BIGINT NOT NULL REFERENCES capability(id),
    raw_text      TEXT NOT NULL,        -- 该 feature 里支撑这个能力的原话
    confidence    NUMERIC(5,4),
    review_status TEXT NOT NULL DEFAULT 'proposed'
                  CHECK (review_status IN ('proposed','confirmed','dismissed')),
    PRIMARY KEY (feature_id, capability_id)
);
```

**关联挂在 `requirement_feature` 上（而不是 REQ 上）是本方案的核心决定**，理由：feature 已经有一整套生命周期（`status` / `origin_version_no` / `removed_version_no`）。需求更新后不再支持某能力 → 该 feature 被软删 → **能力关联自动失效，不需要任何新代码**。这正好回答了你说的「不支持 pdf 导出了，也能把来源删掉」。

### 3.3 新增：条件的受控匹配与待确认

```sql
-- AI 抽出的原始条件 → 若匹配不上词表，进这里待人工确认
CREATE TABLE constraint_candidate (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    raw_constraint TEXT NOT NULL,
    suggested_key  TEXT,
    capability_id  BIGINT REFERENCES capability(id),
    source_id      BIGINT REFERENCES requirement_source(id) ON DELETE CASCADE,
    status         TEXT NOT NULL DEFAULT 'pending_confirmation'
                   CHECK (status IN ('pending_confirmation','accepted','rejected')),
    created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### 3.4 扩展：`requirement_master`（= 需求主线）

```sql
ALTER TABLE requirement_master
    ADD COLUMN IF NOT EXISTS stream_title TEXT,          -- 见 §9-8：与 requirement_name 的关系待定
    ADD COLUMN IF NOT EXISTS primary_capability_id BIGINT REFERENCES capability(id);
```

⚠️ **`primary_capability_id` 单列只承载「主能力」**，多能力需求要靠 `feature_capability` 反查（见 §9-2）。

### 3.5 扩展：`requirement_version`（= 版本时间轴）

```sql
ALTER TABLE requirement_version
    ADD COLUMN IF NOT EXISTS capability_snapshot JSONB NOT NULL DEFAULT '[]',  -- 能力快照
    ADD COLUMN IF NOT EXISTS constraint_snapshot JSONB NOT NULL DEFAULT '[]',  -- 条件快照
    ADD COLUMN IF NOT EXISTS is_current BOOLEAN NOT NULL DEFAULT FALSE;
```

**快照为什么必须单独存 JSONB，而不是每次从 feature 派生**：因为 `module_key`（或未来的条件词表）是会变的。今天把「按部门筛选」改叫「按部门维度筛选」，所有历史版本的派生结果会**一起变**——历史就被污染了。存快照是把「当时怎么理解的」钉死。

`is_current` 是冗余字段（`master.current_version` 已经能表达），但你的设计里明确要求，且能让「某主线当前版本」的查询免一次 JOIN。**注意它需要一个「同 stream 只有一个 true」的保证**，建议用部分唯一索引：
```sql
CREATE UNIQUE INDEX uq_version_current ON requirement_version (requirement_id) WHERE is_current;
```

## 4. 旧数据迁移

现有数据量很小（4 REQ / 5 版本 / 24 feature / 8 source），**迁移风险很低**，但仍要按你的原则「现有需求历史不能丢失」处理。

| 步骤 | 内容 | 是否破坏性 |
|---|---|---|
| 1 | 加列（`ADD COLUMN IF NOT EXISTS`，全部带默认值） | 否 |
| 2 | 建新表（能力 / 条件 / 关联 / 候选） | 否 |
| 3 | ~~回填历史版本的能力/条件快照~~ | **不做**——见下 |
| 4 | 对**当前 active 的 24 条 feature** 跑一次能力抽取，产出 `proposed` 关联 | 否（只新增行） |
| 5 | 人工在审核页逐条确认/驳回能力归属 | 否 |

**第 3 步为什么不回填**：历史版本（v1）当时并没有能力概念，硬造一份「v1 的能力快照」等于**编造历史**。更诚实的做法是快照列留空，并在 UI 上区分「此版本早于能力模型上线，无快照」。

这与你「历史不能被污染」的原则是一致的——**空着比编一个更干净**。

**回滚预案**：所有改动都是 `ADD COLUMN` / `CREATE TABLE`，不删列不改类型。回滚只需 `DROP` 新对象，现有 24 条 feature 与 5 个版本不受影响。

## 5. 新需求进入时，如何判断「新建主线」还是「追加版本」

你的三分支，**现有机制已经实现了其中两条**：

| 分支 | 现有机制 | 状态 |
|---|---|---|
| 追加到已有主线 → 生成新版本 | `review.target_requirement_key` 非空 → `commit_requirement_node` 不新建 master，`version_no = current_version + 1` | ✅ **已实现**（E 批刚打通前端入口） |
| 与已有需求关联，但不修改原需求 | `requirement_relation`（`proposed` 待人工裁决） | ✅ 已实现 |
| 创建新主线 | `target_requirement_key` 为空 → `allocate_key()` 分配 `REQ-{6位}` | ✅ 已实现 |

**所以要补的只有「判断」这一步**——即：分析阶段给出建议「应追加到 REQ-000015」还是「新建」，带置信度，低置信度转人工。这正好落在现有审核页上（和 E 批的合并入口并排）。

判定规则（你的原则 §四.2）：

> **不能仅凭能力名称判断是否属于同一条版本链。**

所以判定输入至少要有：**能力** + **业务对象**（`(动作, 对象)` 里的对象）+ 现有主线的标题/正文。即：

```
新需求：(导出, Excel)，业务对象 = 员工数据
REQ-000002：(导出, Excel)，业务对象 = 员工数据   → 同一业务对象 → 建议追加版本
REQ-000015：(导出, Excel)，业务对象 = 订单数据   → 不同业务对象 → 建议新建主线
```

**这里有个待确认点**：「业务对象」从哪来？现有抽取没有这个字段（只有 `business_domain`，且是 auth/order/report 这种粗粒度领域分类）。见 §9-4。

## 6. 需要改动的 API / Agent / 审核流程

### 6.1 抽取（`skills/prompts.py` + `agents/extract_agent.py`）

现状输出 10 个字段。建议**新增**（不删旧的，符合你的原则 2）：

```
- capability：本条功能的能力，形如 {"action": "导出", "object": "Excel"}
- constraints：限定条件列表，**只能从给定词表里选**，形如 ["按部门筛选"]
- raw_constraint：若条件匹配不上词表，输出原文（进入待确认）
```

并把**现有能力/条件词表**注入 prompt（这一步是防漂移的关键。不给词表让模型自由发挥，必然裂成「导出Excel / Excel导出 / 支持导出Excel」）。

**风险**：现在 prompt 已经在输出 `modules` 了，再加三个字段可能让模型漏字段或乱填。**建议先做一个小实验**（拿现有 24 条 feature 的真实文本跑一遍，看输出稳定性），再决定是否合进同一个 prompt，还是拆成第二次调用。

### 6.2 审核流程（`api/routes/reviews.py` + `commit_nodes.py`）

- 审核页新增一块「**能力归属**」：显示 AI 提议的 `(动作, 对象)` 与条件，人可确认/改选/驳回
- 新增「**主线判定建议**」：建议新建 / 建议追加到 REQ-xxxxx（带置信度）
- `commit_requirement_node` 落库时额外写 `feature_capability` 与版本快照

**注意事务边界**：能力关联必须与 feature 落库**同事务**（现有 `commit_requirement_node` 全程用调用方 session，新写入必须延续这个约定，不要自建 session——`relation.update_status` 就是自建 session 的反例，E 批为此专门加了 `confirm_many(session=...)`）。

### 6.3 只读查询（新增，不破坏现有）

| 端点 | 作用 |
|---|---|
| `GET /capabilities` | 能力词表（供前端下拉、供 prompt 注入） |
| `GET /constraints` | 条件词表 |
| `GET /capabilities/{id}/streams` | 按能力搜需求主线（**你的搜索需求 1**） |
| `GET /capabilities/{id}/streams?constraints=按部门筛选` | 能力 + 条件联合搜（**搜索需求 2**） |
| `GET /requirements/{key}/capabilities` | 某主线的能力与条件 |
| `PATCH /feature-capabilities/{...}` | 人工裁决能力归属 |

**检索现状的限制**：`RetrievalService.search` 的向量分支是**需求级**（`requirement_embedding` 一条 REQ 一条），`search_features` **只有 ILIKE、没有向量**。所以「按能力 + 条件搜」如果走能力表 JOIN，是精确匹配，够用；但如果要「原文兜底」（你的搜索需求 3），feature 级没有向量，只能 ILIKE。**要不要给 feature 加向量，是个成本决策**，见 §9-7。

### 6.4 前端（`static/js/app.js`）

- 详情页：在「当前功能明细」上方加「能力 / 条件」区块
- 需求库：筛选区加「能力」「条件」两个下拉（现有 7 项筛选加 2 项）
- 审核页：合并入口旁加「能力归属」确认区

## 8. 兼容性风险

| # | 风险 | 说明与对策 |
|---|---|---|
| 1 | **prompt 膨胀** | 抽取 prompt 要注入能力/条件词表。词表变大后 prompt 会膨胀，且模型可能开始漏字段。对策：词表只注入**相关**的（按业务域过滤或向量召回 top-N），并在批次 2 实测 |
| 2 | **`business_domain` 语义重叠** | 现有 `business_domain`（auth/order/report…，单值）与新「能力」在概念上有重叠。**建议保留不动**，明确分工：`business_domain` 是粗粒度领域，能力是细粒度功能。不要试图合并 |
| 3 | **`requirement_review` 无索引** | 它没有 `source_id` 索引。能力归属若要关联审核记录，JOIN 会慢。**建议本次顺带补索引**（纯新增，零风险） |
| 4 | **版本表无状态列** | 你的设计要 `status` + `is_current`。现有 `change_type` 是「本版本做了什么变更」，**不是状态**，不要混用 |
| 5 | **`requirement_master.status` 与版本 `is_current` 的职责划分** | `master.status ∈ (active/archived/deleted)` 是主线级；版本级是另一回事。要明确「主线 archived 时其版本 `is_current` 怎么处理」 |
| 6 | **能力抽取会引入新的 LLM 调用成本** | 每次提交多一次调用（或 prompt 变长）。当前 `requirement_embedding` 走 outbox 异步，能力抽取建议也走异步，避免拖慢提交响应（渠道要求 3 秒内应答） |
| 7 | **前端零自动化测试** | 现有前端没有任何测试，改动只能靠浏览器手验。批次 4/5 的验证成本会集中在人工走查上 |

## 9. ❗ 设计歧义清单（**请你拍板，我不自行决定**）

按「会卡住实现」的严重程度排序。

### 9-1 ❗ 你的设计图里没有「模块」，但对话里一直有——两者对不上

你的图是：
```
能力
  └── 需求主线
```
「能力」在最顶层。但前几轮我们说的是「**模块 → 能力 → 需求**」，而且你在最初的需求里说「AI 自动检测出**模块**，相似的需求放在一个模块中」。

同时，现有 D 批已经有 `requirement_feature.module_key`（REQ-000015 有「巡检任务模块/问题上报模块/统计报表模块/权限管理模块」），那是**需求内部的功能分组**。

**三种可能，含义完全不同**：
- (a) 「模块」= 能力的上级（模块 → 能力 → 主线），需要新建 module 表
- (b) 「模块」就是「能力」，只是叫法不同
- (c) 「模块」= 现有 `feature.module_key`（需求内部分组），与跨需求的能力是**两套独立的东西**

**我倾向 (c)**：两者层级不同（一个在需求内、一个跨需求），不该混为一谈，也不该合并。但这直接决定要不要新建 module 表，**必须你定**。

### 9-2 ❗ `capability_id` 单列装不下多能力需求

你的 `requirement_streams` 里有单个 `capability_id`。但 **REQ-000015 有 13 条功能、4 个模块**，不可能只有一个能力。

- 如果它表示「**主能力**」→ 语义是什么？谁来选？
- 如果一条主线真的只有一个能力 → 与「一个文档分好多子模块」矛盾

**我建议**：`capability_id` 降级为可空的「主能力」，真实的多对多用 `feature_capability`（§3.2）反查。**请确认。**

### 9-3 ❗ 条件是修饰「哪个能力」的？你的 `version_constraints` 缺一个维度

你写的是 `version_constraints(version_id, constraint_id)`。但用你自己的例子：

> v2：增加按部门筛选

这个「按部门筛选」修饰的是 **「导出员工数据」这个能力**，不是版本里的其它能力。一个版本有多个能力时，`(version_id, constraint_id)` 无法表达「是哪个能力的条件」。

**建议改成三元组** `(version_id, capability_id, constraint_id)`。**请确认。**

### 9-4 「业务对象」从哪来？

你的规则「不能仅凭能力名称判断是否属于同一条版本链」，靠的是**业务对象不同**（员工数据 vs 订单数据）。但现有抽取**没有这个字段**。

- 要新加字段吗？（类似 `capability` 那样抽 `business_object`）
- 还是复用 `requirement_title` / `business_domain`？

**这个是主线判定的核心输入，不定就没法判。请指示。**

### 9-5 能力本身是受控词表吗？

你明确说「AI 不允许直接自由创建**正式条件**」。**但能力呢？** 你没说。

- 如果能力也不许自由创建 → 需要「新增能力申请 → 人工确认」流程，与条件对称
- 如果能力可以自由创建 → 会漂移（导出Excel / Excel导出 / 支持导出Excel）

**我倾向能力和条件一样受控**（都用 `(action, object)` 精确匹配，天然抗漂移），但这会带来「动作词表」的维护成本。**请确认。**

### 9-6 「审核记录」在版本上只能间接到达

你的设计图里「审核记录」挂在版本下。但现有 `requirement_review` 的外键是 **`source_id`**，不是 `version_id`。要拿到「某版本的审核记录」得走 `version → version_source → source → review` **两跳**。

- 接受两跳（不改表）
- 还是给 `requirement_review` 加 `version_id`（需要回填历史）

**请指示。**

### 9-7 要不要给 feature 加向量？

你的搜索需求 3「原文搜索」——现有 `search_features` **只有 ILIKE，没有向量**（向量只有需求级 `requirement_embedding`）。

- 不加 → 搜「按区域层级导出」这类没进词表的表述会漏
- 加 → 新增一张 feature 级向量表 + outbox 任务 + 回填

**成本差异明显，请指示。**

### 9-8 `version_label` 与现有 `version_title` 的关系

你的表里两个都有（`version_no` + `version_label`），现有已有 `version_title`（如「门店巡检管理系统 V1.0 需求」）。

是需要一个**可自定义的展示标签**，还是 `v1/v2/v3` 就够？（后者可以直接由 `version_no` 派生，不必存列。）
