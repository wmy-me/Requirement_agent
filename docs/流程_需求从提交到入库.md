# 流程：一条需求从提交到入库

> **用途**：把「需求怎么进来、怎么被分析、怎么变成正式需求」这一整条链路讲清楚。
> 写给接手的人，也写给要判断「哪些环节能交给模型」的人。
> 写于 2026-09-16，**所有结论都对着代码核过**，关键的都标了 `文件:行号` 可自行验证。
>
> 配套阅读：`docs/current-state.md`（现在有什么）、`docs/api-contract.md`（接口什么样）、
> `docs/方案_Agent工具层.md`（为什么模型不写库）。

---

## 0. 三句话

1. **系统有两张图。** 分析图（`extract → retrieve → analyze → risk → decide`）里**模型参与**，
   但它**一行业务数据都不写**；决定图（`record → commit/reject`）里**没有模型**，
   正式需求的全部写入都在这里。
2. **两条入口**（同步 HTTP / 异步渠道）在「分析」处汇合、共用同一个方法，行为完全一致。
3. **没有任何一条路径能让模型直接写库。** 正式需求（`requirement_master`）的每一行，
   都必须**人点一次「通过」**才存在 —— **新建也一样，没有例外**。

---

## 1. 谁做什么：三个角色

这是理解整条链路的关键 —— 三方职责边界非常硬：

| 角色 | 负责 | **绝对不做** |
|---|---|---|
| **模型（LLM）** | 把文本变成结构化判断：抽取需求、判重复/关联/冲突、评风险 | **不写任何业务数据**。「这条需求和谁重复」是它的输出，不是它的动作 |
| **确定性代码** | 检索、阈值判定、版本计算、落库、审计、发向量 | 不做「理解」类判断 |
| **人** | **决定这条需求成不成立、并到哪条主线、微调哪些功能** | 不需要读代码 |

> 模型在整条链上只被调用 **3 次**（`extract_skill.py:142`、`analyze_skill.py:58`、
> `risk_skill.py:53`），**全在分析图里，全都不写业务数据**。

## 3. 第一段：进来 + 分析

### 3.1 两条入口，一个归属地

| 入口 | 端点 | 特点 |
|---|---|---|
| **同步** | `POST /api/v1/requirements/submit` | 提交后**等分析跑完**才返回，响应里直接带 analysis / risk |
| **同步（multipart）** | `POST /api/v1/requirements/ingest` | 支持文本 + 文件，文件走解析器抽正文 |
| **异步** | `POST /api/v1/channels/feishu/webhook` | **立即返回**，分析由后台补 |

**异步为什么必须立即返回**：飞书事件订阅（HTTP Webhook 与长连接两种模式）都要求在
**3 秒内**应答，而分析图要跑 **4 个 LLM 步骤**，等不起。

异步链路是：
```
webhook → ChannelIngestService.ingest()
        → 落 source(received)          ← 只写这一张表
        → OutboxRepository.enqueue(event_type="requirement_analysis")
        → 立即返回
                    ⋮（后台）
   OutboxConsumer（跑在 API 进程的 lifespan 线程里，api/app.py:56-61）
        → RequirementAnalysisTask → RequirementService.process_requirement(source_id)
        → 与同步路径**共用** _analyze_and_mark_pending()
```

> **两条入口在 `_analyze_and_mark_pending` 汇合**（`requirement_service.py:103`），
> 所以「同步提交」与「飞书进来的」分析行为完全一致 —— 这是刻意的，避免两条路各长各的。

### 3.2 第一步：落一条「来源」

```python
saved_source = self.source_repo.save(source)     # INSERT INTO requirement_source
```

此时 `processing_status = 'received'`。**注意这时它还什么都不是** ——
只是一条「有人说了一件事」的记录，跟正式需求库没有任何关系。

幂等：`requirement_source.idempotency_key` 上有唯一索引，同一 (渠道 + 发起人 + 正文摘要)
重复提交不会产生第二条。

### 3.3 分析图五步（`workflows/graphs.py:25`）

| 节点 | 谁做 | 读什么 | 产出 |
|---|---|---|---|
| `extract` | **模型** | 只有原文 | 结构化需求（标题/摘要/业务对象/功能条目/模块） |
| `retrieve` | **确定性代码** | 抽取出的摘要 | 语义相近的历史需求候选（**写死 `limit=5`**） |
| `analyze` | **模型** | 抽取结果 + 上一步的候选 | 重复/关联/冲突/独立 + 理由 + 候选评分 + 主线建议 |
| `risk` | **模型** | 抽取结果 | 质量/变更/技术影响三类风险 |
| `decide` | **纯规则** | 分析 + 风险 | 要不要人审（**恒为要**，见下） |

**边的顺序是写死的**：

```python
graph.add_edge(START, "extract")
graph.add_edge("extract", "retrieve")
graph.add_edge("retrieve", "analyze")
graph.add_edge("analyze", "risk")
graph.add_edge("risk", "decide")
```

**模型不决定「先查什么、再查什么」** —— 那是编排的事。模型只是图里几个节点的内部实现，
一个「文本进 → JSON 出」的函数。

### 3.4 模型在这条链上的完整形态

**调用（三处，同一条路）**：

```python
# skills/base_skill.py:22
def _generate_json(self, prompt, system_prompt):
    if not self.provider.is_configured():
        raise RuntimeError("LLM provider is not configured")
    text = self.provider.generate(prompt, system_prompt=system_prompt)
    candidate = self._extract_json_block(text)      # 正则抠 JSON
    if not isinstance(candidate, dict):
        raise ValueError("LLM response was not a JSON object")
    return candidate
```

**数据怎么进去**：编排查好、序列化成 JSON 文本，拼进 prompt。

```python
# skills/prompts.py 的 build_analyze_user_prompt 末尾
f"当前需求：{extracted_json}\n"
f"历史需求：{history}"
```

模型看到的是**一坨文本**，不是结构化输入。**它没有「再查一次」的通道** ——
想要更多信息，做不到。

**输出怎么出来**：正则从返回文本里抠 JSON 块（```json … ``` 或首个 `{` 到末个 `}`），
再 `json.loads`。所以 prompt 里才要反复写清楚字段名 ——
**那不是「定义工具」，那是用文字约定一个输出格式然后自己解析**。

**失败怎么办**：整体回退，不做「半模型半规则」。

```python
except Exception as exc:
    # 不做“半模型半规则”混用，失败时整体回退，保证结果语义稳定。
    logger.warning("event=skill_fallback skill=analyze error=%s", exc)
    return fallback
```

另外 `LLMProvider.is_configured()` 为假时（没配 key），直接走 `_heuristic_analyze`
的本地规则 —— 所以**没有大模型也能跑**，只是判断质量不同。

### 3.5 第一段结束时，库里多了什么

| 表 | 变化 |
|---|---|
| `requirement_source` | +1 行，`processing_status = 'pending_review'`，`metadata` 里装满了分析结果 |
| **`requirement_master`** | **没动** |
| **`requirement_feature`** | **没动** |
| **`requirement_version`** | **没动** |

**换句话说：跑完四个 LLM 步骤、花掉几万 token，正式需求库里一行都没多。**
这不是 bug，是设计 —— 见 §9。

## 4. 人在哪里介入

前端右侧「待办」tab → `GET /api/v1/reviews/pending` 拉出所有 `pending_review` 的来源。

审核人看到的是**完整的证据面板**（都在 `metadata` 里）：

| 路径 | 内容 |
|---|---|
| `metadata.extracted` | 抽取出的结构化需求 |
| `metadata.analysis` | 重复/关联/冲突判断 + 候选 + 理由 + **主线建议** |
| `metadata.risk` | 三类风险 |
| `metadata.capability_match` | 命中/新提议的能力与条件 |

然后他做**三个决定之一**：

| decision | 后端行为 |
|---|---|
| `approved` | 进 **commit** 分支 → **正式落库** |
| `rejected` | 进 **reject** 分支 → 来源置 `rejected`，**不创建任何需求** |
| `returned` | 同上，置 `returned`（退回去补充） |

## 5. 第二段：审核决定（图 B）

### 5.1 入口与事务边界

```
POST /api/v1/reviews/submit
  → ReviewService.submit_decision(...)          ← 事务外壳
       开 session → 跑决定图 → commit / rollback / close
```

`ReviewService` 是**唯一**开事务的地方；图里的节点不 commit，只干活。

### 5.2 决定图（`graphs.py:46`）

```python
graph.add_node("record",  record_review_node)
graph.add_node("commit",  commit_requirement_node)
graph.add_node("reject",  reject_requirement_node)
graph.add_edge(START, "record")
graph.add_conditional_edges("record", route_decision,
                            {"commit": "commit", "reject": "reject"})
```

```python
def route_decision(state):
    """approved 走 commit，其余审核结果统一走 reject 分支。"""
    return "commit" if _ctx(state).get("decision") == "approved" else "reject"
```

**只有 `approved` 能进 commit。** 这是全系统**唯一的**写入闸门。

### 5.3 `record` 节点

校验来源状态（必须是 `pending_review`，否则报错 → 路由层翻 409），
写一条 `requirement_review` 留痕（谁、什么时候、什么决定、什么意见）。

### 5.4 `commit` 节点 —— 真正的写入（`commit_nodes.py:381`）

进来先做一件事：**决定这条需求是「新建」还是「并入既有」**。

```python
target_key = ctx.get("requirement_key")     # 审核请求里的 target_requirement_key
if target_key:
    master = master_repo.get_by_key(target_key)   # 并入既有
# 查不到 → master 保持 None → 走新建
```

然后按 `current_version` 分三条支路处理**功能条目**（`commit_nodes.py:429-465`）：

| 条件 | 走哪条 | 语义 |
|---|---|---|
| `current_version == 0` | `create_features` | **新建 REQ**：来源的功能整体作为本版新增 |
| `feature_overrides` 非空 | `apply_overrides` | **人工逐条裁决**：明确给出 add/modify/delete/keep，优先于自动 diff |
| 其余 | `sync_features` | **自动合并**：按内容哈希匹配；`merge_mode=replace` 时才 prune |

接着依次写：

```python
version_repo.supersede_current(...)   # ① 先把旧的 current 降级（必须在插入前！）
version_repo.save(version)            # ② INSERT requirement_version
master_repo.save(master, ...)         # ③ INSERT/UPDATE requirement_master（带乐观锁 CAS）
relation_repo.upsert_many(...)        # ④ 关系边（proposed）
audit_repo.record(...)                # ⑤ 审计
outbox_repo.enqueue(...)              # ⑥ embedding_sync（向量重算）
```

> ⚠️ **① 必须在 ② 之前**：`uq_version_current` 是部分唯一索引（同主线只允许一个 current），
> 而 `save` 插入时状态默认就是 `current` —— 顺序反了会在第二条版本上撞唯一约束。

### 5.5 新建 vs 合并：两条支路的差别

| | 新建（`target_requirement_key` 为空） | 合并（非空） |
|---|---|---|
| REQ 编号 | `allocate_key()` 从序列取新的（`REQ-{6位}`） | 用既有的 |
| 需求名 | 用来源标题 | **保持目标不变**（只有人工显式改写才跟随） |
| 功能 | 全部 `add` | 按匹配得到 add/modify/delete/keep |
| 版本号 | 从 v1 开始 | `current_version + 1` |
| 关系边 | 会写（分析出的重复/关联） | **会确认**目标与其它重复候选的关系 |

### 5.6 `reject` 节点

来源置 `rejected` / `returned` + 写审计。**不创建版本、不碰需求主表。**

## 6. 一次「新增」到底写了哪些行

以「提交一条全新需求 → 审核通过」为例：

| 时刻 | 表 | 操作 | 关键字段 |
|---|---|---|---|
| 提交 | `requirement_source` | **INSERT** | `processing_status='received'` |
| 分析完 | `requirement_source` | UPDATE | `status='pending_review'`，`metadata` 装满分析结果 |
| 审核点通过 | `requirement_review` | **INSERT** | 决策留痕 |
| 〃 | `requirement_master` | **INSERT** | +1 行，`current_version=1`, `lock_version=1` |
| 〃 | `requirement_feature` | **INSERT** ×N | 每个功能一行，`origin_version_no=1` |
| 〃 | `requirement_version` | **INSERT** | `version_no=1`, `change_type='new'` |
| 〃 | `requirement_version_source` | **INSERT** | 版本 ← 来源 |
| 〃 | `requirement_relation` | INSERT（可能） | 分析出的关系边，`status='proposed'` |
| 〃 | `audit_event` | **INSERT** | |
| 〃 | `outbox_event` | **INSERT** | `embedding_sync` → 后台算向量 |

**注意顺序**：`requirement_master` / `feature` / `version` 三张表**全部只在最后一步**
（审核通过）才被写入。在人工点「通过」之前，这三张表跟这条需求完全无关。

## 7. 并发：两个人同时点「通过」会怎样

**G 批（2026-09-16）之前**：后者的写入**静默覆盖**前者 —— 谁最后写谁赢，没有任何提示。

**现在**：`master_repo.save(expected_lock_version=...)` 做 CAS
（Compare-And-Swap）：

```sql
INSERT INTO requirement_master AS rm (...) VALUES (...)
ON CONFLICT (requirement_key) DO UPDATE SET ..., lock_version = EXCLUDED.lock_version
WHERE rm.lock_version = :expected_lock_version     -- ← 条件不成立就不更新
RETURNING ...
```

- 期望值取自**本次事务开头**读到的 `lock_version`
- 条件不成立时**该行不更新、`RETURNING` 不返回它** → 抛 `ConcurrentModificationError`
- 整个事务回滚，**败者的工作一点都不会留下**，路由层翻 409

所以现在两人同时点通过：**一个成功，另一个拿到「该需求已被他人修改，请重新加载后再审核」**。

## 8. 为什么不让模型直接写

这条线在代码里被守了不止一处：

1. **结构上**：模型只在分析图里，而分析图**没有任何写业务数据的代码路径**
2. **闸门上**：决定图只认 `decision == "approved"`，而这个值只能来自
   `POST /reviews/submit` —— 一个需要人点的接口
3. **命名上**：`RequirementService.submit_requirement` 的 docstring 明写
   「不会直接写入正式需求主表；审核通过后才生成 REQ」
4. **工具层**（2026-09-16）：`read_only` 恒为 True，**裁决类能力一个都没做成工具**，
   唯一写入口是 `submit_requirement`（也只写「待审来源」）

**为什么这么严**：错误合并会污染整条版本链，错误拆分会造成重复需求 ——
这两种错误**不可自动回滚**，且会随时间累积（后续版本都建在错误的主线上）。
所以「模型给建议、人做决定」不是保守，是这个领域的正确做法。

## 9. 常见误解

| 误解 | 实际 |
|---|---|
| 「跑完分析需求就进库了」 | ❌ 跑完只是 `pending_review`，主表一行没动 |
| 「新建需求不需要审核，合并才需要」 | ❌ **两者都要**。新建走的是同一个 commit 节点，只是 `current_version=0` 那条支路 |
| 「模型判断重复就会自动合并」 | ❌ 模型只输出 `duplicate: true`；合并是人在审核页选的目标 REQ |
| 「`submit_requirement` 会把需求写进需求库」 | ❌ 它只写 `requirement_source`（`received`） |
| 「分析图里有 Agent，所以 Agent 在操作数据库」 | ❌ Agent 是「文本进 JSON 出」的函数，操作数据库的是编排与仓储层 |
| 「回滚是 undo」 | ❌ 回滚是 append-only 的 revert：**产出一个新版本**，历史一行不改（G 批） |

## 10. 这套结构改起来要注意什么

| 想改的东西 | 会牵动什么 |
|---|---|
| 分析图加/减节点 | `graphs.py` 的边 + 状态字段 + `agents_nodes.py`；**这是被测试钉得最死的部分** |
| 让模型决定查什么 | 那就是工具层批次 3（真 function calling），**会动 `LLMProvider` 与推理链路** |
| 加一个「免审核」的快通道 | ⚠️ **强烈不建议** —— 等于拆掉 §8 的全部四道防线。真要做，先想清楚「错误合并谁负责」 |
| 改 `commit_requirement_node` 的写入顺序 | ⚠️ `supersede_current` 必须在 `save` 之前（§5.4） |
| 给模型加写库工具 | 同上，见 `docs/方案_Agent工具层.md` §2.2 |
