```bash
createdb requirement_agent
for f in migrations/0*.sql; do psql -d requirement_agent -f "$f"; done
```

> **编号规则（事实惯例，2026-09-17 补记）**：只追加、不改旧文件。
> 需要改已有对象（约束、索引）时，在新迁移里 `DROP ... IF EXISTS` 再建，
> 或用 `DO $$ ... $$` 判存在 —— 见 `002` / `011` / `020` / `021` 的写法。
> ⚠️ `021` 里有一条**只能判存在、不能 DROP 再建**：`agent_run_run_id_key`
> 一旦建出，就会被同迁移建的两个外键依赖，`DROP CONSTRAINT` 会报
> `DependentObjectsStillExist`，重跑直接失败。

> **关于时间口径**：所有时间列都是 `timestamptz`，存的是绝对时刻。`010` 把数据库
> 默认时区设为 `Asia/Shanghai`，是为了让**不经应用直接连库**（DBeaver / psql）的人
> 看到本地时间；此前默认 `Etc/UTC`，看到的时间会早 8 小时，像是数据错了。
> 应用自身的连接显式带 `-c timezone=UTC`，行为不受影响。

## 向量维度与索引：当前决策

三张表的向量列（`requirement_embedding` / `document_chunk` / `memory_note`）在 `006`
之后统一为 `vector(4096)`。

**决策：保持 4096 维，不建向量索引，走全表精确扫描。** 理由：

- pgvector 的 HNSW / IVFFlat 索引维度上限是 **2000**，4096 维根本建不了索引 ——
  这正是 `006` 删掉三个 1536 维时代索引的原因，不是遗漏。
- 本项目数据量在百级，`ORDER BY embedding <=> $1 LIMIT k` 的精确扫描召回无损，
  且比近似索引更准，量级上完全够用。

**若将来要重建索引**，唯一路径是先降到 ≤2000 维：换一个维度 ≤2000 的 embedding 模型，
或对现有向量做降维（如 Matryoshka 截断）。那需要一次破坏性迁移（改列类型 → 清空向量 →
重建索引 → 用 `scripts/reindex_embeddings.py` 回填），属于独立决策，不要在没评估召回损失前动手。

### 维度必须两处一致

`EMBEDDING_DIMENSION`（`.env` / `settings.py`）必须等于列维度 **4096**。
两者不一致时写入要么被数据库直接拒绝，要么（凑巧同维时）成为检索不到的脏数据。
`EmbeddingService.embed` 会在维度不符时直接抛错，不再静默写库。
